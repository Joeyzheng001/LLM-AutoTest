## 一、Why（为什么做）

当前接口测试面临三个核心痛点：

1. **接口文档缺失**：团队 Java 多仓库体系下无统一接口文档，测试用例编写依赖人工阅读代码
2. **无沉淀资产**：无历史测试用例、无历史缺陷数据，测试工作每次从零开始
3. **LLM 能力未被利用**：团队已具备 Prompt Engineering / LLM API 调用能力，且公司现有 GLM-5.3 可直接使用

## 二、Phase 1 交付块（做什么）

### 目标（可量化）

| # | 目标 | 量化指标 | 验证方式 |
|---|------|----------|----------|
| G1 | 交付可运行的系统 | 覆盖 5 种协议 × 6 环节闭环，每个环节至少 1 个场景跑通 | 验收日现场演示 |
| G2 | 需求文档解析 | 支持 Word / Markdown / Excel 3 种格式输入 | 解析产物抽查 |
| G3 | 接口逆向解析 | 对指定 Java 多仓库（≥2 个）完成代码扫描与接口还原 | 还原结果人工抽查 |
| G4 | Code Review 三视图 | 风险清单、遗漏功能清单、逐条需求-代码映射表 3 种产出全部生成 | 产物完整性检查 |
| G5 | 自动化率实测 | 完成度量方案设计，并在验收演示中实测出第一个数值 | 度量报告 |
| G6 | 周期约束 | 一周内完成全部交付 | 里程碑检查 |

### 范围（MVP）

- **输入通道**：需求文档三格式解析 + Java 多仓库扫描
- **处理流水线**：Code Review → 用例生成 → 自动执行 → 测试报告 → 缺陷清单 → 回归沉淀
- **度量体系**：9 节点口径定义 + 验收演示实测
- **技术基线**：GLM-5.3 + pytest + Python 主体 + Java 解析服务 + Vue 前端
- **组织形式**：4 人全时投入，多角色协作

## 三、Phase 2 Backlog（后续做什么，占位）

- 生产级成熟度打磨（稳定性、性能、大规模并发）
- 历史数据资产建设（历史用例、缺陷库）
- 跨团队推广
- 缺陷管理系统对接（Jira 等）
- 需求变更增量处理

## 四、不做清单（明确不做什么）

| # | 非目标 | 说明 |
|---|--------|------|
| N1 | 首版不做生产级成熟度打磨 | 各环节跑通即可 |
| N2 | 不做 UI 测试 / 性能测试 / 安全测试 | 严格限定在接口测试自动化范围 |
| N3 | 不做 LLM 训练 / 微调 | 仅使用现有 GLM-5.3 的推理能力 |
| N4 | 不做幻觉问题的系统性应对 | LLM 幻觉治理方案不在本次范围 |
| N5 | 不做接口文档治理 | 不输出或维护 Swagger/OpenAPI 文档 |
| N6 | 不做合规 / 安全审查建设 | 已确认无合规要求 |
| N7 | 不做历史数据资产建设 | 无历史用例、无缺陷库，不回补 |
| N8 | 不做跨团队推广 | 产出仅面向测试团队内部 |
| N9 | 不做缺陷管理系统对接 | 仅生成本地缺陷记录文件 |
| N10 | 不做需求变更的增量处理 | 输入变更即整体重跑对应节点 |

## 五、成功标准

- G1 为核心目标，G6 为刚性约束
- G2–G5 为验收细节
- 验收演示当天全流程跑一遍，实测自动化率数值
