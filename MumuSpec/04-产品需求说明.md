## 一、产品场景

### 场景 1：需求输入与解析

**用户**：测试专项小组成员
**目标**：将 Word / Markdown / Excel 格式的需求文档转化为结构化需求条目
**流程**：
1. 用户上传需求文档（三格式之一）
2. 系统解析文档，抽取功能点
3. 系统输出结构化需求条目 JSON（requirements.json）
4. 下游环节消费标准化输入

### 场景 2：代码扫描与接口还原

**用户**：测试专项小组成员
**目标**：在无接口文档的前提下，从 Java 多仓库代码中逆向还原接口定义
**流程**：
1. 用户指定 Java 仓库路径（≥2 个）
2. 系统扫描仓库，汇总源码清单（code_inventory.json）
3. LLM 从源码中逆向还原接口定义（路径、方法、入参、出参、协议类型）
4. 系统输出结构化接口清单（interfaces.json）

### 场景 3：Code Review 三视图

**用户**：测试专项小组成员
**目标**：对照需求文档核查代码实现，产出三种视图
**流程**：
1. 系统逐条比对需求条目与接口/代码实现
2. 产出需求-代码映射表（mapping.json）
3. 从映射表派生风险清单（risk_list.json）
4. 从映射表派生遗漏功能清单（missing_features.json）
5. 一次生成、三种视图输出

### 场景 4：用例生成与执行

**用户**：测试专项小组成员
**目标**：LLM 基于还原的接口定义自动生成可执行测试脚本，并无人值守执行
**流程**：
1. LLM 基于 interfaces.json + requirements.json 生成测试脚本
2. 每接口生成 ≥3 条用例（正常/边界/异常各 ≥1）
3. 执行引擎一键触发全量用例执行
4. 输出结构化执行结果（execution.json）

### 场景 5：测试报告与缺陷闭环

**用户**：测试专项小组成员
**目标**：自动生成测试报告，失败用例转化为缺陷清单并支持复测
**流程**：
1. 执行结束自动生成测试报告（Markdown + JSON）
2. 失败用例自动转化为缺陷记录
3. 对已修复缺陷，一条命令发起复测
4. 复测通过的用例自动沉淀为回归脚本

### 场景 6：度量与验收

**用户**：测试团队负责人
**目标**：实测自动化率数值，支撑项目结论
**流程**：
1. 验收当天全流程跑一遍
2. 记录各节点是否人工介入
3. 产出自动化率 = 无人工节点数 / 9
4. 对人工介入节点给出瓶颈原因分析

## 三、用户流程总览

```
需求文档（Word/MD/Excel）
    ↓
[需求解析] → requirements.json
    ↓
Java 多仓库代码
    ↓
[代码扫描] → code_inventory.json
    ↓
[接口逆向还原] → interfaces.json
    ↓
[Code Review] → mapping.json + risk_list.json + missing_features.json
    ↓
[用例生成] → 测试脚本 + cases.json
    ↓
[执行引擎] → execution.json
    ↓
[测试报告] → report.md + report.json
    ↓
[缺陷闭环] → defects.json → [复测] → [回归沉淀]
    ↓
[度量] → 自动化率数值
```
