## 1. 采用的方案

仓库采用**环境变量优先、配置文件兜底**的跨语言配置策略：Python（orchestrator）通过 `dataclass` + `os.environ` 显式读取；Java（java-parser）使用 Spring Boot 的 `@ConfigurationProperties` 绑定 `application.yml`；前端（frontend）在构建期硬编码代理目标。所有运行时参数统一通过 `docker-compose` 的 `environment` / `env_file` 注入，`.env.example` 作为共享模板。

## 2. 关键文件与位置

- `services/orchestrator/src/orchestrator/config.py`：Python 侧唯一配置入口，定义 `Settings` dataclass，提供 `from_env()` 工厂方法。
- `services/java-parser/src/main/resources/application.yml`：Spring Boot 默认配置，声明 `server.port` 与 `parser.scan-concurrency`。
- `services/java-parser/src/main/java/com/llmautotest/parser/ParserProperties.java`：以 `@ConfigurationProperties(prefix = "parser")` 将 YAML 字段映射为强类型 record，并在构造器中校验正数。
- `deploy/docker-compose.yml`：编排层唯一事实来源，集中注入 `JAVA_PARSER_URL`、挂载 `artifacts` 卷、按 profile 启用可选服务。
- `deploy/.env.example`：LLM 调用参数模板（`LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL_NAME`、`LLM_TEMPERATURE`、`LLM_TOP_P`、`LLM_SEED`）。
- `services/frontend/vite.config.ts`：开发期代理配置，指向 `http://localhost:8000`。
- `services/orchestrator/tests/test_config.py`：覆盖必填缺失报错、默认值、敏感信息过滤等配置行为。

## 3. 架构与约定

### 3.1 Python（orchestrator）
- `Settings` 是 `frozen=True` 的不可变 dataclass，所有字段均为运行时必需或带默认值的可选项。
- 必填项（`JAVA_PARSER_URL`、`LLM_BASE_URL`、`LLM_SEED` 可选）缺失时 `from_env()` 抛出 `RuntimeError`，错误消息包含缺失键名，禁止静默默认。
- 可选项提供合理默认值：`PORT=8000`、`ARTIFACTS_ROOT=/data/llm-autotest`、`LLM_MODEL_NAME=glm-5.3`、`LLM_TEMPERATURE=0.2`、`LLM_TOP_P=0.8`。
- `public_summary` 属性用于日志输出，刻意不包含 `LLM_API_KEY` 等密钥字段，测试断言其不含任意 secret 字符串。
- LLM 采样参数（temperature/top_p/seed）被文档标记为“禁止硬编码”，必须经环境变量传入。

### 3.2 Java（java-parser）
- 使用 Spring Boot 标准方式：`application.yml` 中 `parser.scan-concurrency` 通过 `@ConfigurationProperties(prefix = "parser")` 绑定到 `ParserProperties.scanConcurrency`。
- 构造器内校验 `scanConcurrency > 0`，非法值抛 `IllegalArgumentException`，确保并发度受控可配置。
- 端口通过 `server.port` 暴露，容器映射为 8081:8080。

### 3.3 部署与注入
- `docker-compose.yml` 是配置注入的唯一入口：orchestrator 通过 `environment.JAVA_PARSER_URL` 直连 java-parser，并通过 `env_file: .env` 加载 LLM 凭据。
- 产物目录统一挂载为 `/data/llm-autotest`，各服务共享同一 volume `artifacts`。
- 可选服务（test-executor、mock-services）通过 `profiles: ["exec"]` / `["mock"]` 按需启用。

### 3.4 前端
- 仅开发期存在代理配置，生产构建未体现环境变量注入，当前为占位实现。

## 4. 约束与规则

- **禁止硬编码 LLM 采样参数**：`config.py` 注释与 `.env.example` 注释均引用 docs/09 第五章，要求 temperature/top_p/seed 必须来自环境变量。
- **禁止静默默认必填项**：`test_config.py` 断言缺失 `JAVA_PARSER_URL` 时抛出含键名的 `RuntimeError`。
- **日志安全口径**：`public_summary` 不得包含 API Key 等敏感字段，由单元测试强制验证。
- **LLM 模型冻结**：默认 `LLM_MODEL_NAME=glm-5.3`，注释明确“仅允许 GLM-5.3（冻结基线）”。
- **并发度受控**：`ParserProperties` 构造器强制 `scanConcurrency` 为正整数。
- **编排即配置**：`docker-compose.yml` 注释称其为“编排唯一事实来源”，服务间 URL、端口、卷路径均在此集中声明。
- **产物路径统一**：volume 挂载点固定为 `/data/llm-autotest`，由 compose 与 orchestrator 默认值共同保证一致。

## 5. 现状与缺口

- 前端尚未接入运行时配置，仅保留开发代理。
- test-executor 服务暂未在 compose 默认 profile 中启用，依赖契约待定稿。
- 配置未引入 schema 校验框架（如 pydantic settings），仅靠 dataclass + 手动转换与测试覆盖。
- 无集中配置中心或 KV 存储，所有配置均以环境变量形式注入容器。
