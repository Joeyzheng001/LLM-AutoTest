## 1. 整体方法
本仓库包含 Python（FastAPI）、Java（Spring Boot）和前端 TypeScript 三个子服务，错误处理采用“轻量、显式”的方式：没有统一的错误码枚举、全局异常处理器或中间件，而是通过各语言标准异常 + 数据类不变量校验来保证输入/状态正确性。

## 2. 关键文件与位置
- `services/orchestrator/src/orchestrator/config.py`：Settings.from_env 在缺失必填环境变量时捕获 KeyError 并包装为 RuntimeError 抛出（`raise RuntimeError(msg) from exc`），测试通过 `pytest.raises(RuntimeError, match="JAVA_PARSER_URL")` 验证。
- `services/test-executor/src/executor/result.py`：定义 `FailureKind`（`assertion` / `environment`）与 `CaseResult`，在 `__post_init__` 中用 `ValueError` 强制“通过的用例不得携带失败类型”，实现断言失败与环境失败的二态分离。
- `services/java-parser/src/main/java/com/llmautotest/parser/ParserProperties.java`：使用 record 构造器校验 `scanConcurrency > 0`，非法值直接 `throw new IllegalArgumentException(...)`。
- `services/orchestrator/src/orchestrator/api.py`：FastAPI 路由仅做协议转换，当前 `/health` 与 `/api/v1/pipeline/nodes` 未引入业务异常路径。
- `services/java-parser/src/main/java/com/llmautotest/parser/HealthController.java`：Spring Boot 健康检查端点，无自定义异常处理。
- `services/frontend/src/App.vue`：前端目前仅为占位，无错误处理逻辑。

## 3. 架构与约定
- **配置层集中报错**：Python 侧将环境变量缺失统一在 `Settings.from_env` 处捕获并转为 `RuntimeError`；Java 侧通过 `@ConfigurationProperties` + record 构造器校验参数合法性，两者都在“启动/初始化阶段”尽早失败。
- **结果模型内嵌不变量**：`CaseResult.__post_init__` 用 `ValueError` 维护“passed 与 failure_kind 互斥”的不变量，使上层无需重复判断。
- **失败分类语义化**：`FailureKind` 明确区分“断言失败”（计入通过率分母）与“环境失败”（隔离至待环境确认，不计入通过率分母），由 `ExecutionSummary` 提供数值汇总口径（F-RPT-02）。
- **HTTP 层保持薄**：orchestrator 的 FastAPI 路由注释强调“只做协议转换与校验，业务下沉 service”，当前未定义全局异常转换器或统一响应体。
- **前端不计算数值**：`App.vue` 注释规定“数值一律来自后端 API，前端不做计算”，因此前端错误处理尚未成为关注点。

## 4. 约定与约束
- 缺失必填环境变量必须显式报错，禁止静默降级（`config.py` 中 `except KeyError` 后 `raise RuntimeError`，并由单元测试覆盖）。
- 执行结果必须通过 `CaseResult` 构造，禁止绕过 `__post_init__` 的不变量校验；违反时抛出 `ValueError`。
- Java 配置字段必须在 record 构造器中校验范围，非法值抛 `IllegalArgumentException`。
- HTTP 接口当前仅暴露健康检查与节点清单，未定义业务错误码或统一错误响应结构——这是当前阶段的实现事实，而非已文档化的规范。
- 前端尚无错误处理代码，相关约定以注释形式约束“数值来源必须走后端 API”。

总体而言，该仓库的错误处理处于早期阶段：核心集中在配置校验与结果模型不变量上，尚未建立跨服务的统一错误类型、错误码体系或全局异常中间件。
