# MumuSpec 十四文档工作流规则

本规则整合 `mumu-spec-main`、`mumu-spec-init`、`mumu-spec-r1-proposal`、`mumu-spec-r2-align`、`mumu-spec-r3-design`、`mumu-spec-r4-finalize`、`mumu-spec-sync`、`mumu-spec-check`、`mumu-spec-status`、`mumu-spec-tasks` 十个 Skill 的铁律、门禁与流程。

与 [docs/09_开发规范说明.md](docs/09_开发规范说明.md)、[docs/06_需求定稿冻结.md](docs/06_需求定稿冻结.md)、[llm-integrity.md](llm-integrity.md) 冲突时以后者为准。

## 一、全局铁律（不可违反）

1. **真源目录**：`MumuSpec/`（兼容 `Spec模板/`）下 `01`～`14` 的 `.md`。
2. **写作顺序**：R1 → R2 → R3 → R4（见 01 第十一节），**不要**按编号 01→14 顺序硬写。
3. **契约真源**：对外字段以 **09** 为准，存储以 **10** 为准。
4. **OpenSpec**：只作变更壳；合并结果回写 01～14（如项目启用 OpenSpec，需另行约定映射）。
5. **写作铁律**（写入 01 总则）：
   - PRD 不写 SQL：04 不出现 CREATE TABLE、SELECT 等语句
   - API 不写像素：09 不描述 UI 布局、颜色、间距
   - 契约真源：对外字段以 09 为准，存储以 10 为准
   - 不混层：用户故事不写接口细节，接口规格不写用户价值
   - 写作顺序：R1→R2→R3→R4，不按 01→14 编号顺序硬写

## 五、四轮工作流

### R1 — 需求采集与立项（02 → 03 → 04）

- **02**：结构化会议纪要、邮件、访谈，标出来源与「下一步」
- **03**：Why、Phase 1 交付块、Phase 2 Backlog（占位）、成功标准、风险、立项前置
- **04**：产品场景、用户流程、功能列表；**不写** SQL、接口 path、像素级 UI

**输出质量**：
- 03 的「不做」至少 3 条，避免范围蔓延
- 04 不出现 09 级接口细节或表字段名
- 03→04 追溯字段一致（成功标准能落到后续 P0/P1）

**完成后**：进入 R2（05 + 09）。若仅有模糊想法，先停在 R1，不要提前写 09。

### R2 — 对齐（05 ↔ 09）

- **05**：REQ-*、US-*、AC-*；每条故事含功能/设计/验证对齐列
- **09**：path、方法、参数、**示例请求/响应/错误体**；字段名在此 **冻结**
- **互校准**：每条 P0 AC 能在 09 找到可观测断言（状态码、字段、错误码）

**不混层**：
- 05 不写 SQL、不写完整 JSON Schema 重复（引用 09 章节）
- 09 不写用户价值叙事（留在 05/04）

**完成后**：进入 R3（08/10/06/07/11）。若仅改一个 endpoint，改完后建议 sync。

### R3 — 展开（08 + 10 → 06 + 07 + 11）

| 文档 | 写什么 |
|------|--------|
| 08 | 组件、部署、技术选型、与外部系统边界 |
| 10 | 表/集合、字段、索引、约束；字段名与 09 一致 |
| 06 | 界面状态、交互、异常分支；引用 05 的 US/REQ |
| 07 | 性能、可用性、审计等 NFR；可被 13 验证 |
| 11 | 认证、授权、威胁与缓解；与 07 安全类不重复堆砌 |

**推荐顺序**：08 → 10 → 06 → 07 → 11

**步骤**：
1. 读 01 铁律：PRD 不写 SQL、API 不写像素
2. 06 每条异常路径对应 05 AC 或注明「见 US-xxx」
3. 10 每个持久化字段能在 09 DTO/响应中找到或说明内部字段
4. 更新各篇变更记录

**完成后**：进入 R4（12/13/14）。

### R4 — 收口（12 + 13 → 14）

- **12**：里程碑、WBS、依赖；P0 能力对齐 03 Phase 1
- **13**：测试分层（L1～L4）、TC-*、门禁（G-LINT / G-UNIT / G-INT 等）；每条 TC 指回 05 REQ 与 09 可断言字段
- **14**：四向追溯（REQ ↔ US ↔ API/Rule ↔ TC）；发布前终检表

**终检清单（必须输出）**：
- [ ] 每条 P0 US 在 14 有行
- [ ] 每条 REQ 在 13 有 ≥1 TC
- [ ] 09 示例请求/响应/错误齐全
- [ ] 10 索引与约束齐全
- [ ] 03 Phase 1 与 05 P0 范围一致

**完成后**：大改动走 sync；可选更新 spec-manifest.json 节点状态。

## 六、变更联动（sync）

| 变更类型 | 先改 | 再改 |
|----------|------|------|
| 行为、AC、US | 05（06 若已有细节） | 09/10 若契约变 → 13 → 14 |
| API 字段、path、错误码 | 09 | 10 → 05 AC → 13 TC → 14 |
| 表结构、存储 | 10 | 09 → 13 → 14 |
| 仅测试/门禁 | 13 | 14 |
| 范围增删 | 03 → 04 | 05 → 下游全套 |
| 排期 | 12 | 通常不动契约 |

**工作流**：
1. 问清：改了哪一份、哪一节、什么 ID
2. 输出联动清单（表格：编号 | 动作 | 原因），等用户确认
3. 逐文件修改，**不**引入第二套 REQ 前缀
4. 最后输出终检 mini 清单（同 R4 五条门禁）

**不做**：
- 不替 R1～R4 从零新建整套（应转对应 round Skill）
- 不修改 MumuSpec/ 之外的文件，除非用户明确要求

## 七、质量检查（check）

### 1. 完整性检查
- 01-14 文档是否都存在
- 每个文档的元数据表是否填写完整
- 变更记录表是否有内容
- 03 的"不做清单"是否 ≥ 3 条
- 09 的每个 API 是否有请求/响应/错误示例

### 2. 一致性检查
- REQ 编号全局唯一（无重复）
- US 编号全局唯一
- API 编号全局唯一
- TC 编号全局唯一
- 03 Phase 1 范围 ↔ 05 P0 用户故事范围一致
- 09 API 字段名 ↔ 10 数据模型字段名对齐
- 05 AC 描述 ↔ 09 API 行为对应

### 3. 可追溯性检查
- 14 追溯矩阵完整性：每行填满 REQ | US | API | TC
- 每个 P0 REQ 在 13 中至少对应 1 个 TC
- 每个 US 在 14 中有行
- 无孤立的 REQ/US/API/TC（未追溯到其他文档）
- 02 的每条需求在 03 中有对应

### 4. 质量规则检查
- AC 中无模糊词（友好、快速、尽量、可能、适当）
  - 错误示例："系统快速响应"
  - 正确示例："系统响应 < 200ms"
- 每个 AC 可测试（能通过/失败判断）
- 09 的每个 API 路径符合 RESTful 规范
- 10 的每个表有主键和索引定义
- 07 NFR 指标可量化（不用"高性能"，用"P99 < 200ms"）

**问题分级**：
- P0（必须修复）：文档缺失、编号冲突、追溯断裂
- P1（建议修复）：模糊词、缺少示例、元数据不完整

**状态建议**：
- 有 P0 问题 → 保持 Draft
- 无 P0 且 P1 < 3 → 可进入 Review
- 全部通过 → 可标记 Approved

## 八、版本状态（status）

| 状态 | 含义 | 操作 |
|------|------|------|
| Draft | 草稿，正在编辑 | 可继续修改 |
| Review | 审查中 | 等待团队审查 |
| Approved | 已批准 | 可交付，变更需走 propose 流程 |
| Deprecated | 已废弃 | 不再使用 |

**数据源**：
1. MumuSpec/ 下各文档的元数据表
2. 每个文档的"变更记录"表
3. 变更提案目录（如使用 OpenSpec）

## 九、任务拆分（tasks）

### 拆分维度

**按技术栈分层**：
- 后端任务：API 实现、业务逻辑、数据库操作、缓存策略
- 前端任务：页面开发、组件实现、API 对接、交互逻辑
- 数据任务：表结构创建、索引优化、数据迁移脚本
- 测试任务：单元测试、集成测试、压力测试

**按依赖关系排序**：
- 第一优先级（基础设施）：数据库表创建、API 契约定义、基础服务搭建
- 第二优先级（核心功能）：业务逻辑实现、前后端对接
- 第三优先级（增强功能）：性能优化、监控告警、文档完善

### 拆分原则

**必须遵守**：
1. 每个 Task 必须可独立完成和测试
   - 错误："开发后端"
   - 正确："实现库存扣减 API"
2. Task 粒度适中：最小 0.5 天，最佳 2-3 天，最大 5 天（需进一步拆分）
3. 明确依赖关系：标注前置任务，识别可并行任务
4. 关联 Spec 文档：每个 Task 必须追溯到 US，列出关联的 TC

**避免的错误**：
1. Task 过大（> 5 天）
2. Task 之间依赖不清
3. 没有明确的验收标准
4. 未关联到 Spec 文档
5. 忽略测试任务

### 每个 Task 必须包含

- 来源（关联 US 编号）
- 可验证的验收标准
- 预估工作量（天）
- 依赖关系
- 关联文档（05/09/10/13）

**完成后**：
- 将任务清单写入 12-实施计划与里程碑.md
- 或保存为独立文件 sprint-backlog.md
- 提示用户确认任务拆分是否合理
- 建议按依赖关系排序执行
