# 任务拆分

## 职责

将 05 用户故事拆分为可执行的开发任务清单，生成 Sprint Backlog。

## 输入

- `05-用户故事与验收标准.md`（必须）
- `09-API接口规格.md`（参考）
- `10-数据模型与存储规格.md`（参考）
- `12-实施计划与里程碑.md`（可选，已有计划时）

## 拆分维度

### 1️⃣ 按技术栈分层

**后端任务**：
- API 实现
- 业务逻辑
- 数据库操作
- 缓存策略

**前端任务**：
- 页面开发
- 组件实现
- API 对接
- 交互逻辑

**数据任务**：
- 表结构创建
- 索引优化
- 数据迁移脚本

**测试任务**：
- 单元测试
- 集成测试
- 压力测试

### 2️⃣ 按依赖关系排序

**第一优先级**（基础设施）：
- 数据库表创建
- API 契约定义
- 基础服务搭建

**第二优先级**（核心功能）：
- 业务逻辑实现
- 前后端对接

**第三优先级**（增强功能）：
- 性能优化
- 监控告警
- 文档完善

## 执行步骤

1. **读取用户故事**
   - 解析 05 中所有 US（按 P0/P1/P2 分组）
   - 提取每条 US 的 AC

2. **分析依赖关系**
   - 识别技术依赖（如：前端依赖 API）
   - 识别业务依赖（如：订单依赖库存）
   - 构建依赖图

3. **拆分任务**
   - 每条 P0 US 拆分为 3-5 个 Task
   - 每条 P1 US 拆分为 2-3 个 Task
   - 每个 Task 必须：
     - 有明确来源（关联 US 编号）
     - 有可验证的验收标准
     - 预估工作量（天）
     - 标注依赖关系

4. **生成任务清单**

## 拆分原则

### ✅ 必须遵守

1. **每个 Task 必须可独立完成和测试**
   - ❌ 错误："开发后端"
   - ✅ 正确："实现库存扣减 API"

2. **Task 粒度适中**
   - 最小：0.5 天（太小）
   - 最佳：2-3 天
   - 最大：5 天（需进一步拆分）

3. **明确依赖关系**
   - 标注前置任务
   - 识别可并行任务

4. **关联 Spec 文档**
   - 每个 Task 必须追溯到 US
   - 列出关联的 TC

### ❌ 避免的错误

1. Task 过大（> 5 天）
2. Task 之间依赖不清
3. 没有明确的验收标准
4. 未关联到 Spec 文档
5. 忽略测试任务

## 使用场景

- **Sprint 规划**：从 Spec 生成开发计划
- **任务分配**：明确责任和工作量
- **进度跟踪**：Task 完成情况对应 US 进度
- **AI Coding**：AI 按 Task 逐个实现代码

## 完成后

- 建议按依赖关系排序执行
