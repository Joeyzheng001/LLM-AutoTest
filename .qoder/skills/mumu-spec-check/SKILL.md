# Spec 文档质量检查

## 职责

对 Spec 01-14 文档进行全面质量检查，输出健康度报告。

## 检查维度

### 1️⃣ 完整性检查

- [ ] 01-14 文档是否都存在
- [ ] 每个文档的元数据表是否填写完整（模块编号/名称/版本/状态）
- [ ] 变更记录表是否有内容
- [ ] 03 的"不做清单"是否 ≥ 3 条
- [ ] 09 的每个 API 是否有请求/响应/错误示例

### 2️⃣ 一致性检查

- [ ] REQ 编号全局唯一（无重复）
- [ ] US 编号全局唯一
- [ ] API 编号全局唯一
- [ ] TC 编号全局唯一
- [ ] 03 Phase 1 范围 ↔ 05 P0 用户故事范围一致
- [ ] 09 API 字段名 ↔ 10 数据模型字段名对齐
- [ ] 05 AC 描述 ↔ 09 API 行为对应

### 3️⃣ 可追溯性检查

- [ ] 14 追溯矩阵完整性：每行填满 REQ | US | API | TC
- [ ] 每个 P0 REQ 在 13 中至少对应 1 个 TC
- [ ] 每个 US 在 14 中有行
- [ ] 无孤立的 REQ/US/API/TC（未追溯到其他文档）
- [ ] 02 的每条需求在 03 中有对应

### 4️⃣ 质量规则检查

- [ ] AC 中无模糊词（友好、快速、尽量、可能、适当）
  - ❌ 错误示例："系统快速响应"
  - ✅ 正确示例："系统响应 < 200ms"
- [ ] 每个 AC 可测试（能通过/失败判断）
- [ ] 09 的每个 API 路径符合 RESTful 规范
- [ ] 10 的每个表有主键和索引定义
- [ ] 07 NFR 指标可量化（不用"高性能"，用"P99 < 200ms"）

## 执行步骤

1. **扫描文档目录**
   - 检查 `MumuSpec/`（或 `Spec模板/`）目录下 01-14 的 `.md` 文件
   - 统计存在/缺失数量

2. **逐项检查**
   - 按上述 4 个维度逐一验证
   - 记录每个问题点

3. **分类问题**
   - 🔴 **P0**（必须修复）：阻断性问题
     - 文档缺失
     - 编号冲突
     - 追溯断裂
   - 🟡 **P1**（建议修复）：质量问题
     - 模糊词
     - 缺少示例
     - 元数据不完整
   - 🟢 **通过**：符合要求

4. **生成报告**

## 使用场景

- **交付前体检**：标记 Approved 前必须运行
- **日常巡检**：团队协作时定期检查
- **变更后验证**：修改文档后确认一致性
- **培训演示**：展示 AI 自动发现问题的能力

## 完成后

- 如有 P0 问题 → 建议保持 **Draft** 状态
- 如无 P0 且 P1 < 3 → 可进入 **Review** 状态
- 如全部通过 → 可标记 **Approved**
- 提示用户运行 `/mumu-spec-status` 查看整体状态
