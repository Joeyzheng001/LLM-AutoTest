## 模块 0：流程编排总控（ORCH）

**对应**：E-METRIC-03（验收编排）、G1 闭环串联

### 功能清单

| 编号 | 功能 | 对应 UserStory |
|------|------|---------------|
| F-ORCH-01 | 统一入口命令：串联"需求解析 → 代码扫描 → 接口还原 → Code Review → 用例生成 → 执行 → 报告 → 缺陷清单"全流程 | E-METRIC-03 |
| F-ORCH-02 | 节点级断点续跑：任一节点产物已存在时可跳过该节点 | E-METRIC-03 |
| F-ORCH-03 | 节点人工介入标记采集：节点执行日志自动记录 + 运行后人工标注复核（半自动方案，见 R-ORCH-03，对应评审 TA-03） | E-METRIC-01、E-METRIC-02 |

### 交互规则

- R-ORCH-01：上游节点产物未生成时，下游节点拒绝启动并报错指明缺失项（E-METRIC-03）
- R-ORCH-02：各节点间以文件为接口（结构化 JSON 落盘到固定目录），节点内不依赖内存传递（E-METRIC-03）
- R-ORCH-03：人工介入判定 = 节点开始到结束期间，除启动命令外发生任何人工文件修改或命令干预（E-METRIC-01）；采集方式为半自动：编排器自动记录节点执行日志（含命令清单与产物变更时间戳），流程运行后由人工按日志标注复核并确认，标注结果计入自动化率（对应评审 TA-03 降级方案）

### 边界与异常分支

- X-ORCH-01：某节点失败 → 停止后续节点，输出失败节点 + 原因，已产出节点产物保留（E-METRIC-03）
- X-ORCH-02：断点续跑采用固定 Schema，不引入版本号比对机制：产物 Schema 校验不通过 → 拒绝复用，强制重跑该节点（对应评审 TA-08 简化）
- X-ORCH-03：全流程完成但某节点被标记降级（见 X-EXEC-03）→ 报告中生成"降级说明"章节（E-METRIC-03）

## 模块 1：需求解析（REQ）

**对应**：E-REQ-01

### 功能清单

| 编号 | 功能 | 对应 UserStory |
|------|------|---------------|
| F-REQ-01 | Word（.docx）需求文档解析：抽取功能点为结构化需求条目 JSON | E-REQ-01 |
| F-REQ-02 | Markdown（.md）需求文档解析：同构产物 | E-REQ-01 |
| F-REQ-03 | Excel（.xlsx）需求文档解析：同构产物 | E-REQ-01 |
| F-REQ-04 | 需求条目 Schema 校验：三格式产物过同一 Schema | E-REQ-01 |

### 交互规则

- R-REQ-01：输入 = 文件路径列表；输出 = `requirements.json`（每条含：条目 ID、标题、描述、优先级标记）
- R-REQ-02：条目 ID 全局唯一、跨格式稳定（用于映射表与用例溯源）
- R-REQ-03：解析策略 = 文本抽取 + LLM 结构化；Prompt 模板验收前锁定版本（验收输入锁定，见 E-METRIC-03 AC1），不做 Prompt 变更回归验证集（对应评审 TA-05 减负）
- R-REQ-04：三格式样例文档均预置 golden 基准（人工预标注的期望条目数与关键条目清单），AC1 比对对象为预置基准而非现场人工判断（对应评审 TE-01）

### 边界与异常分支

- X-REQ-01：文件不存在 / 扩展名不符 → 明确报错退出（退出码非 0，stderr 含错误类别关键字 `[REQ-ERROR]`），不产出空 JSON（AC4）
- X-REQ-02：文档无功能点内容（空文档/纯图表）→ 报错"未识别到需求条目"（退出码非 0，stderr 含 `[REQ-ERROR]`，判定形式同 X-REQ-01）（AC4）
- X-REQ-03：LLM 解析超时 → 重试 1 次，仍失败则该文件标记失败，不阻塞其他文件（AC4）
- X-REQ-04：混排内容（表格+正文混合功能点）→ 允许条目粒度不完美，但需记录解析置信度标记供人工抽查参考

## 模块 2：代码扫描（CODE）

**对应**：E-CODE-01

### 功能清单

| 编号 | 功能 | 对应 UserStory |
|------|------|---------------|
| F-CODE-01 | 多仓库扫描：遍历 ≥2 个 Java 仓库，汇总源码文件清单 | E-CODE-01 |
| F-CODE-02 | 扫描范围过滤：按目录/后缀（.java）过滤，排除测试代码与生成代码目录 | E-CODE-01 |
| F-CODE-03 | 产出源码清单 `code_inventory.json`（仓库、模块、文件路径） | E-CODE-01 |

- R-CODE-01：输入 = 仓库本地路径列表（启动命令参数）；输出 = 结构化清单

## 模块 3：接口逆向还原（REV）

**对应**：E-CODE-02（最高风险项 R2）

### 功能清单

| 编号 | 功能 | 对应 UserStory |
|------|------|---------------|
| F-REV-01 | REST 接口还原：从 Controller/注解代码还原路径、方法、入参、出参 | E-CODE-02 |
| F-REV-02 | 非 REST 协议接口还原：gRPC（proto/service）、SOAP（WSDL/实现类）、MQ（Listener/Producer）中至少识别 1 种（与 E-CODE-02 AC1 口径一致，gRPC 优先；消歧义：是三者中至少一种，非各一种，对应评审 TE-03） | E-CODE-02 |
| F-REV-03 | 接口定义 Schema 化：还原产物过预定义 Schema | E-CODE-02 |
| F-REV-04 | 还原产物 `interfaces.json`：含协议类型、接口签名、代码位置溯源 | E-CODE-02 |

### 交互规则

- R-REV-01：输入 = `code_inventory.json` + 源文件内容；输出 = `interfaces.json`
- R-REV-02：还原策略 = 先静态特征定位（注解/接口定义文件）再 LLM 语义解析，减少全文盲扫
- R-REV-03：每个接口带代码位置（仓库+文件+行号区间），供映射表与人工抽查使用
- R-REV-04：LLM 上下文管理策略（对应评审 TA-02）：① 文件选择——静态特征定位（注解/proto/WSDL 等特征文件）优先，非全文盲扫（衔接 R-REV-02）；② 分块——单次调用仅送入接口定义文件及其直接关联文件（Controller → Service 接口签名 → DTO 定义），关联文件由静态调用链分析确定，不依赖单次大上下文；③ 跨文件信息传递——以中间产物（接口候选清单）落盘，二次调用合并去重；④ 该策略同时作为 token 用量控制手段（对应风险 R8）

### 边界与异常分支

- X-REV-01：单个文件解析失败 → 记录"跳过 + 原因"，不中断整体（AC3）
- X-REV-02：解析出但无法确定参数类型 → 参数标记 `unknown`，进入下游时按边界默认值处理
- X-REV-03：LLM 输出不符合 Schema → 重试 1 次；仍失败则丢弃该接口并记录
- X-REV-04：识别出的接口数 < 5（低于 AC1 底线）→ 输出告警，提示换用兜底演示仓库（对应 R2 应对策略）；兜底仓库的还原结果在报告中单独标注、不计入 G3 达成，且与真实仓库结果分列呈现，避免掩盖真实仓库解析能力结论（对应评审 PM-06/TA-04）

## 模块 4：Code Review（REVIEW）

**对应**：E-REVIEW-01、E-REVIEW-02、E-REVIEW-03（人工审核，对应评审 PM-01）

### 功能清单

| 编号 | 功能 | 对应 UserStory |
|------|------|---------------|
| F-REVW-01 | 需求-代码映射表生成：逐条拆解需求 Claim，并比对 `requirements.json` × `interfaces.json` + 代码实现 | E-REVIEW-01 |
| F-REVW-02 | Claim 级状态标注：已实现 / 部分实现 / 缺失 / 待核查，并汇总到需求级 | E-REVIEW-01 |
| F-REVW-03 | 风险清单派生：从映射表生成风险描述 + 需求条目 + 代码位置 | E-REVIEW-02 |
| F-REVW-04 | 遗漏功能清单派生：提取证据完备且确认缺失的 Claim；证据不足单列为待核查 | E-REVIEW-02 |
| F-REVW-05 | 一次生成四视图：同一 LLM 调用产出需求/Claim 映射表，风险清单与遗漏清单程序化派生；变更范围由双分支 diff 程序化派生 | E-REVIEW-02 |
| F-REVW-06 | LLM 产物人工审核：对 `interfaces.json` / `mapping.json` 等关键产物记录"通过 / 驳回"结论与驳回原因，驳回产物回流至对应生成节点（对应评审 PM-01） | E-REVIEW-03 |

### 交互规则

- R-REVW-01：映射覆盖率必须 100%（每条需求至少有一条 Claim；Claim 状态为已实现 / 部分实现 / 缺失 / 待核查）
- R-REVW-02：风险清单和遗漏功能清单由程序从 Claim 级映射过滤生成（非独立 LLM 调用）；证据不足不得判为已实现或确认缺失
- R-REVW-03：单一 `review_mapping.json` 产物包含映射表、风险清单、遗漏清单、变更范围四个视图
- R-REVW-04："部分实现"条目自动进入风险清单（实现不完整即风险）
- R-REVW-05：人工审核产物为 `review_log.json`（结构化：产物、结论、驳回原因、复审记录）；驳回条目标记"待修正"，回流路径 = 重跑对应生成节点或人工修正后复审；人工审核不在 9 节点自动化率口径内，审核结论仅作为产物质量记录（E-REVIEW-03）

### 边界与异常分支

- X-REVW-01：需求条目找不到任何相关代码，且代码证据范围完整 → Claim 标"缺失"；证据范围不完整 → 标"待核查"
- X-REVW-02：LLM 无法给出实现判断 → Claim 标"待核查"并计入证据风险（不得伪造确定结论）
- X-REVW-03：映射表某条目代码定位失败 → 该 Claim 降级为"待核查"，不阻塞其余条目
- X-REVW-04：需求条目与接口数量悬殊（需求多接口少）→ 正常产出，由遗漏清单体现

## 模块 5：用例生成（GEN）

**对应**：E-TEST-01

### 功能清单

| 编号 | 功能 | 对应 UserStory |
|------|------|---------------|
| F-GEN-01 | 按接口生成用例：每接口 ≥3 条（正常/边界/异常各 ≥1） | E-TEST-01 |
| F-GEN-02 | 用例参数一致性约束：参数名与结构仅来自 `interfaces.json` | E-TEST-01 |
| F-GEN-03 | 生成选定框架语法的可执行脚本 | E-TEST-01 |
| F-GEN-04 | 用例溯源：每条用例携带需求条目 ID + 接口 ID | E-TEST-01、E-REPORT-03 |

### 交互规则

- R-GEN-01：输入 = `interfaces.json` + `requirements.json`（需求用于断言语义）；输出 = 脚本文件 + `cases.json`（用例元数据）
- R-GEN-02：生成后执行程序化校验：参数名 ⊆ 接口定义参数集合，违规用例丢弃重生成（AC2）
- R-GEN-03：脚本必须可被框架加载（语法校验作为生成完成的前置条件，AC3）
- R-GEN-04：边界用例依据参数类型生成默认边界值（数值 0/负数/极值、字符串空/超长、unknown 类型按 null 处理，衔接 X-REV-02）

### 边界与异常分支

- X-GEN-01：某接口生成失败 → 跳过并记录，其他接口不受影响
- X-GEN-02：参数一致性校验连续 2 次不通过 → 该接口用例放弃，记录为"生成质量告警"（对应 R4）
- X-GEN-03：接口定义为 `unknown` 参数（来自 X-REV-02）→ 用例标记"低置信度"，可执行但报告中注明

## 模块 6：执行引擎（EXEC）

**对应**：E-TEST-02、E-TEST-03

### 功能清单

| 编号 | 功能 | 对应 UserStory |
|------|------|---------------|
| F-EXEC-01 | 框架选型：产出选型说明文档（≥2 候选对比） | E-TEST-02 |
| F-EXEC-02 | 一键执行：单命令跑全量用例，无人工操作 | E-TEST-02 |
| F-EXEC-03 | 结构化执行结果：每用例通过/失败 + 失败原因 → `execution.json` | E-TEST-02 |
| F-EXEC-04 | REST 执行：≥5 条用例对真实/Mock 服务执行 | E-TEST-03 |
| F-EXEC-05 | gRPC / GraphQL / SOAP / MQ 执行：各 ≥1 条（Mock 允许）；其中 MQ 以"脚本生成成功 + Mock 执行演示"降级路径为主方案（异步断言成本高，见 X-EXEC-03，对应评审 TA-07） | E-TEST-03 |
| F-EXEC-06 | Mock 服务管理：为不可部署协议提供 Mock 执行环境；MQ 仅提供同步收发级演示 Mock，不做异步消费轮询断言 | E-TEST-03 |

### 交互规则

- R-EXEC-01：执行引擎按协议路由到对应 Runner，Runner 结果统一收敛到同一 `execution.json` 结构
- R-EXEC-02：环境可用性探测优先于执行：REST > gRPC > GraphQL > SOAP/MQ 优先级排序（对应 R3）
- R-EXEC-03：失败用例必须区分"断言失败"与"环境/连接失败"，二者在 `execution.json` 中类型不同（后者不直接进缺陷清单，见 X-DEF-02）
- R-EXEC-04：前置数据准备（对应评审 PM-02）：需鉴权（token/登录态）或上游造数的接口，在 Day 1 环境探测时识别并预置于执行配置（fixtures），执行时自动加载；前置数据准备发生在流程启动前，不计为节点内人工介入（E-TEST-02 AC3）

### 边界与异常分支

- X-EXEC-01：被测服务不可达 → 该协议用例标记"环境失败"，不判为缺陷
- X-EXEC-02：用例执行超时 → 单用例超时上限，超时记失败并附超时原因
- X-EXEC-03：某协议 Runner 未就绪 → 该协议降级为"脚本生成成功 + Mock 执行演示"，报告中注明降级（AC3）
- X-EXEC-04：执行中服务崩溃 → 已完成用例结果保留，剩余用例标记"中断"
- X-EXEC-05：前置数据无法自动准备（依赖外部系统不可用）→ 对应用例标记"前置缺失"跳过并记录，不判为缺陷（对应评审 PM-02）

|------|------|---------------|

- X-RPT-01：`execution.json` 缺失/损坏 → 报告生成失败并报错，禁止产出空报告
- X-RPT-02：全量用例均环境失败 → 报告标注"无可判读结果"，通过率不输出（而非 0%）

## 模块 8：缺陷闭环（DEF）

**对应**：E-REPORT-02

### 功能清单

| 编号 | 功能 | 对应 UserStory |
|------|------|---------------|
| F-DEF-01 | 失败用例 → 缺陷记录：接口、失败原因、复现步骤（用例脚本引用） | E-REPORT-02 |
| F-DEF-02 | 复测命令：对指定缺陷（或全量缺陷）重跑关联用例 | E-REPORT-02 |
| F-DEF-03 | 缺陷状态流转：复测通过 → 关闭建议；仍失败 → 保留 | E-REPORT-02 |

### 交互规则

- R-DEF-01：仅"断言失败"用例进缺陷清单；"环境失败"用例隔离到"待环境确认"列表（衔接 X-EXEC-01）
- R-DEF-02：缺陷与用例通过用例 ID 双向关联，复测即重跑关联用例
- R-DEF-03：状态流转记录时间戳，形成可审计的缺陷生命周期

### 边界与异常分支

- X-DEF-01：复测时被测代码已变更 → 复测结果标注"基于新版本"，提示可能非同一缺陷
- X-DEF-02：复测用例脚本已被人工删除/修改 → 报错指明缺失用例，复测跳过该项
- X-DEF-03：验收闭环依赖人工埋入缺陷（AC3）→ 埋入位置固定为业务逻辑层（在演示仓库独立分支上使接口返回错误数据），埋入方式与预期失败用例写入演示脚本；埋入代码变更不进入被测仓库主干（对应评审 TE-07）

## 模块 9：回归沉淀（REG）

**对应**：E-REPORT-03

### 功能清单

| 编号 | 功能 | 对应 UserStory |
|------|------|---------------|
| F-REG-01 | 复测通过用例自动归档至回归目录 | E-REPORT-03 |
| F-REG-02 | 溯源信息携带：需求条目 ID + 接口 ID 随脚本归档 | E-REPORT-03 |
| F-REG-03 | 回归套件命令：重跑回归目录全量脚本 | E-REPORT-03 |
| F-REG-04 | 回归资产清单：目录结构化 + 资产索引文件 | E-REPORT-03 |

### 交互规则

- R-REG-01：归档 = 移动（非复制）复测通过的脚本至回归目录，原执行目录保持只含未沉淀用例
- R-REG-02：回归目录按协议维度组织（REST/gRPC/GraphQL/SOAP/MQ 子目录）
- R-REG-03：同一用例重复通过复测 → 幂等归档，不产生重复文件

### 边界与异常分支

- X-REG-01：归档时目标已存在同名脚本 → 覆盖并记录版本变更

## 模块 10：度量（MTR）

**对应**：E-METRIC-01、E-METRIC-02

### 功能清单

| 编号 | 功能 | 对应 UserStory |
|------|------|---------------|

| F-MTR-02 | 节点介入采集：消费 F-ORCH-03 的节点日志 + 运行后人工标注复核（半自动，对应评审 TA-03） | E-METRIC-02 |
| F-MTR-03 | 自动化率计算：无人工节点数 / 9（分母固定不缩减，见 X-MTR-01），输出具体数值 | E-METRIC-02 |
| F-MTR-04 | 瓶颈分析报告：人工介入节点的原因归类 | E-METRIC-02 |

### 交互规则

- R-MTR-01：9 节点固定口径：需求解析、代码扫描、接口还原、用例生成、执行、报告、缺陷提交、复测、回归沉淀
- R-MTR-02：采集数据 = 编排器节点执行日志（自动记录）+ 运行后人工标注复核确认（半自动方案，对应评审 TA-03）
- R-MTR-03：瓶颈分析对每个人工介入节点给出"介入原因 + 可自动化路径建议"（对应 R5 应对策略）
- R-MTR-04：项目口径声明（对应评审 PM-03/TE-08）："缺陷提交"节点在本项目中 = 生成本地缺陷记录文件（F-DEF-01），记为自动化节点；生产环境中该节点为人工提交至缺陷管理系统。度量方案文档必须显式声明"项目口径 ≠ 生产口径"，报告解读时不得将本项目自动化率直接外推为生产预期

### 边界与异常分支

- X-MTR-01：某节点被降级跳过（降级分支）→ 该节点按"人工介入"计入（分母固定为 9 不缩减），报告中注明降级节点清单与原因（口径与 E-METRIC-02 AC1 统一，对应评审 TE-02）
- X-MTR-02：节点标记数据缺失 → 自动化率标"数据不完整"，不输出误导性数值
- X-MTR-03：彩排与正式验收各产出一次数值 → 仅正式验收数值作为基线记录
