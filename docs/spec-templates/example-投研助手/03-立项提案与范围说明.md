## 1. 背景与问题

> 描述用户遇到的问题，至少写 2~3 条痛点。参考：信息获取、历史记录、可追溯性、系统可用性。

| 痛点 | 来源 |
|------|------|
| 信息分散：研报、新闻、数据分布在多个系统，无统一问答入口 | `02` S-01 / S-02 |
| 研报阅读耗时、关键信息提取与多份对比依赖人工 | `02` S-01 / S-03 |
| 涉及投研结论时，缺少可复盘的问答与来源标识，复盘成本高 | 场景推演（与 `04` 对齐） |

## 2. 提案概要

> 用 3~5 句话概括要做什么。参考格式："在 XXX 应用内交付 YYY 能力"。要素：会话式问答 · 能力降级 · 可追溯

**Phase 1 预设表述（可按项目改写）**：在投研助手场景下，先交付**统一会话入口 + 可降级问答 + 会话历史落库与查询**，为分析师提供可演示、可测试的最小闭环；**不**在本阶段承诺研报解析流水线、舆情告警与多文档对比表（见上文 Phase 2）。

## 3. 范围边界（与 `02` 采集对齐）

> `02` 中已记录更大范围的投研诉求（解析 / 舆情 / 对比等）。**本套 Spec 模板默认冻结 Phase 1**，避免「采集很大、契约很小」导致读者误判。Phase 2 仅在本文与 `04` 中列表占位，**不**要求同步填满 `09/10` 全量契约。

### 3.1 Phase 1（本版 Must：与 `05`～`09` 示例一致）

| 交付块 | 说明 |
|--------|------|
| 会话管理 | 创建、列表、删除会话 |
| 问答提交 | 绑定 `session_id` 的提问；三级降级（CoPaw → 百炼 → Demo） |
| 历史与追溯 | 按会话查看问答记录；响应含 `traceId`、`answer_source` 等 |
| 能力探测 | `GET …/capabilities`，驱动前端能力状态展示 |

### 3.2 Phase 2（Backlog：采集于 `02`，本版 Out of Scope）

| 方向 | 说明 |
|------|------|
| 研报解析 | PDF/HTML 结构化抽取（标题、评级、目标价、观点等） |
| 深度问答 | 基于语料库的引用级回答、版权与合规策略（需另立专篇或后续迭代） |
| 舆情与对比 | 关键词告警、多研报指标对比、行情多源统一查询 |

### 3.3 简表（范围内 / 范围外）

| 做（Phase 1 内） | 不做（本版明确不做） |
|-----------------|---------------------|
| 会话管理：创建、列表、删除 | 多租户 / 行级数据权限 |
| 问答编排与可观测字段（trace、来源标签） | Phase 2 研报流水线、舆情、对比（见 Phase 2 表） |
| 本地 JSON 存储的教学级持久化 | 生产级高可用集群与审计日志外发 |
| 能力探测与降级策略可验证 | 对接内部行情/交易系统的实时下单能力 |

## 4. 成功标准（可度量）

> 写出 3~4 条可量化的验收标准。句式：用户在 X 分钟内完成 XXX 全链路 / 未配置外部模型时返回 XXX

| 标准 | 度量方式 |
|------|----------|
| 主路径可走通 | 用户在 3 分钟内完成「新建会话 → 提问 → 查看历史」全链路 |
| 未配置外部模型仍可演示 | 无有效 API Key 时，`answer_source=demo` 且接口不抛未处理异常 |
| 能力状态可解释 | 前端能力芯片与 `GET …/capabilities` 字段一致（可截图验收） |
| 追溯字段齐全 | `POST …/ask` 成功响应含 `traceId`、`llm_used`、`answer_source`（与 `09` 一致） |
