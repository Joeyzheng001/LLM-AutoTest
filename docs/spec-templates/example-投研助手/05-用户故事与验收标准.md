> **本文只做一件事**：按用户能理解的子场景拆成多条 **User Story**，并为每条写清 **`REQ-M1QA-{NNN}`**（及必要时 **`RULE-M1-{NNN}`**）、**验收标准（AC）**。

## 字段说明 — 每条 UserStory 必须包含以下字段

| 字段 | 填写说明 | 数据来源 ← | 流向下游 → |
|------|----------|------------|-----------|
| **需求编号** | 唯一编号，如 REQ-M1QA-001 | ← `02` 采集编号 | → `14` 追踪矩阵首列 |
| **故事** | 作为【角色】，我希望【行为】，以便【价值】 | ← `04` PRD 场景拆解 | → `06` FSD 功能点 |
| **优先级** | P0（必须）/ P1（应该）/ P2（可选） | ← `03` 第 4 节 成功标准 | → `12` 里程碑排期 |
| **来源** | 对应 03/04 哪一条需求 | ← `03` 范围 · `04` 场景 | |
| **前置条件** | 触发该故事的前提状态 | ← `04` 用户流程 | → `13` 测试前置 |
| **功能对齐** | 对应功能规格 + 非功能约束 | | → `06` FSD · `07` NFR |
| **设计对齐** | 对应架构、接口、数据、安全 | | → `08` 架构 · `09` API · `10` Data · `11` 安全 |
| **验证对齐** | 对应测试用例 + 追踪矩阵行 | | → `13` TC · `14` 追踪矩阵行 |
| **验收标准** | AC，每条可独立验证 | ← 故事 + `07` NFR | → `13` 测试用例依据 |

## US-004（P1）能力探测与状态展示

| 字段 | 内容 |
|------|------|
| **需求编号** | REQ-M1QA-004 |
| **故事** | 作为**投研用户或演示人员**，我希望**在提问前看到当前可用的模型通道（CoPaw / 百炼 / 离线）**，以便**判断本次回答可信度与是否依赖外部服务** |
| **优先级** | P1 |
| **来源** | ← `03` Phase 1 能力探测 · `04` SC-03 |
| **前置条件** | 前端已加载；可调用后端 |
| **功能对齐** | → `06` Header 能力芯片 · `07` 降级与错误码 |
| **设计对齐** | → `08` Agent 编排 · `09` `GET /api/v1/agent/capabilities` · `10`（无持久化字段） · `11` 密钥不落库 |
| **验证对齐** | → `13` TC-M01-005 · `14` 正向矩阵 |

| 验收标准 | 描述（每条可独立测试） |
|----------|----------------------|
| AC-004-01 | 页面加载或显式刷新后，Header 芯片展示与 `GET /api/v1/agent/capabilities` JSON 字段一致 |
| AC-004-02 | 当百炼未配置时，芯片不得显示「已连接百炼」类误导文案 |
