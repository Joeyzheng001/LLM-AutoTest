# 测试框架选型说明：LLM-AutoTest

- **文档日期**：2026-09-15
- **文档性质**：技术选型结论（对应 [03_用户故事卡片.md](03_用户故事卡片.md) E-TEST-02 AC1、[04_功能规格说明.md](04_功能规格说明.md) F-EXEC-01：产出含 ≥2 候选对比的选型说明文档）
- **变更控制**：属 06 变更控制规则第 2 条允许的例外变更（测试框架选型，G 范围内授权项目内自选）
- **候选**：pytest vs Robot Framework（基于 Python 主栈（[08](08_技术架构与部署方案.md)）排除 Java/JS 系框架）

---

## 一、选型结论

**选定 pytest。**

## 二、需求驱动的评估维度

选型必须服务于本项目的特殊性——**测试脚本由 LLM 生成、须无人值守执行、覆盖五协议**，而非人工编写用例的传统场景：

| # | 评估维度 | 依据 |
|---|----------|------|
| 1 | LLM 生成脚本的可加载性校验成本 | F-GEN-03 / R-GEN-03：脚本必须可被框架加载（语法合法是生成完成的前置条件） |
| 2 | 五协议客户端集成（REST/gRPC/GraphQL/SOAP/MQ） | F-EXEC-06 / R3 降级策略 |
| 3 | 结果结构化导出能力 | F-RPT-02：execution.json 程序化汇总；R-EXEC-03 断言/环境失败二态 |
| 4 | 无人值守执行（headless、无交互） | E-TEST-02 AC1 |
| 5 | 断言失败 vs 环境失败的区分能力 | R-EXEC-03（环境失败隔离至待环境确认） |
| 6 | 一周内团队上手成本 | G6 刚性周期 |

## 三、逐项对比

| 维度 | pytest | Robot Framework |
|------|--------|-----------------|
| LLM 生成可加载性 | **强**：生成目标是纯 Python 代码，语法校验 = `py_compile` / import 收集，程序化判定零歧义；LLM 代码生成生态对 Python 语法最成熟 | 弱：关键字驱动 DSL（表格语法），LLM 需生成符合 RF 语法的 .robot 文件；语法校验需调用 RF 自身的解析器，错误定位对非 RF 熟手不友好 |
| 五协议客户端 | **强**：httpx（REST）、grpcio（gRPC）、gql/ariadne（GraphQL）、zeep（SOAP）、pika（MQ）均为 Python 一等公民，直接 import 进用例 | 中：需将各客户端封装为自定义关键字库（Library），多一层胶水代码，且胶水本身也是维护面 |
| 结构化结果导出 | **强**：pytest-json-report / pytest 插件体系输出机器可读 JSON；亦可自写 plugin hook（`pytest_runtest_logreport`）完全控制 execution.json 结构 | 中：output.xml 需二次解析转换为 execution.json；Rebot 转换链多一环 |
| 无人值守 | **强**：`pytest -q --json-report` 一条命令，headless 天然成立 | 强：`robot --outputdir` 同样成熟（此项持平） |
| 失败二态区分 | **强**：自定义 marker（如 `@pytest.mark.env_failure`）+ exception 分类 + hook 中判定，二态逻辑完全可控 | 中：RF 失败分类需依赖 teardown 关键字或 suite metadata，表达断言失败与环境失败的差异不如代码直接 |
| 上手成本（4 人，一周） | **低**：B/C 为测试开发，Python/pytest 是行业默认技能 | 中：RF 关键字驱动范式对写惯代码的开发者反而不顺手，排查失败用例要理解 RF 执行模型 |
| 与 Monorepo 工具链融合 | **同栈**：ruff/mypy/uv 全覆盖生成脚本本身 | 异栈：.robot 文件游离在 Python 工具链之外，lint/format 管不到 |

## 四、关键决策理由（结合本项目风险）

1. **R2 风险传导链上的减负**：接口还原（R2）已是最重风险，用例生成环节不应再叠加风险。LLM 生成 Python 的可靠性显著高于生成 RF 表格 DSL——后者是低频训练分布，语法错误率会直接拖累 G1 的「跑通」判定；
2. **execution.json 的直通路径**：F-RPT-02 要求数值程序化汇总不经 LLM。pytest 的 hook 体系让 test-executor 服务能从最底层拿到每条用例的原始结果，二态标注（R-EXEC-03）在代码里闭环，不需要解析中间格式；
3. **对 N1（非目标：生产级成熟度打磨）的克制**：RF 的优势在报告美观与关键字复用治理，这些价值要在长期人工维护用例的项目里才兑现；本项目脚本由 LLM 批量生成、按协议归档（R-REG-02），RF 的核心卖点不在这条链路上。

## 五、落地方案（test-executor 服务）

| 项 | 方案 |
|----|------|
| 执行命令 | `pytest <脚本目录> -q --json-report --json-report-file=execution_raw.json`（无人值守口径） |
| 可加载性校验 | 生成完成前置：`python -m py_compile` + pytest 收集阶段零 error（R-GEN-03） |
| 二态标注 | 自定义 pytest plugin：断言失败默认 `assertion`；网络/连接类异常映射 `environment`（`FailureKind` 骨架已就位于 [services/test-executor](../services/test-executor)） |
| 汇总 | test-executor 从 raw report 程序化汇总为 `execution.json`（F-RPT-02：不经 LLM） |
| 归档 | 按 R-REG-02 协议维度组织 pytest 脚本目录；回归重跑即对归档目录再次执行 pytest（F-REG-03） |

## 六、被否决的其他候选（简评）

- **JUnit/TestNG（Java 系）**：与 Python 主栈（08 技术定稿）冲突，脚本生成生态割裂，直接排除；
- **Vitest/Jest（JS 系）**：同上，且被测系统非前端，无收益；
- **HttpRunner**：中文生态友好，但框架活跃度与五协议（尤其 SOAP/MQ）覆盖不及直接写 Python 客户端，pass。
