## 一、9 节点编排状态机（甲实现，乙丙知悉）

### 1.1 状态与判据

节点四态沿用 [pipeline.py](../services/orchestrator/src/orchestrator/pipeline.py) 的 `NodeStatus`：`pending / running / completed / manual_intervention`。

**「已完成」的唯一判据是产物**：节点对应产物文件存在 **且通过对应 Schema 校验**，才允许置 `completed`。任何「代码跑完了但产物没过校验」的情况一律不算完成（诚实红线：不截取可用部分）。

| 节点（顺序固定，R-MTR-01） | 完成判据（产物文件） |
|------|------|
| req_parse | `requirement_items.json` 过 [requirement_items.json](../schemas/requirement_items.json) 校验 |
| code_scan | `code_inventory.json` 过校验 |
| interface_reconstruct | `interface_candidates.json` + `interfaces.json` 均过校验 |
| code_review | `review_mapping.json` 过校验（04 的 R-REVW-03 三文件名是草案表述，以 schemas/ 冻结的单产物口径为准：三视图作字段——mappings/risks/missing_features，风险与遗漏清单程序化派生） |
| testcase_generate | `testcases.json` 过校验（`loadable` 全部为真才计 completed，否则见 1.3） |
| auto_execute | `execution.json` 过校验（**允许有失败用例**——失败二态明确即完成，D4 口径） |
| test_report | `test_report.md` 存在且含真实/兜底分列（D5）+ `metrics.json` 过校验（报告节点双产物：MD 面向人工、JSON 程序化汇总，R-RPT-02） |
| defect_list | `defects.json` 过校验 |
| retest_regression | `regression_index.json` 过校验 |

### 1.2 断点续跑

- 续跑入口收到 `job_id` 后按 NODE_ORDER 顺序扫描产物：连续通过校验的节点直接标 `completed` 并跳过，**从第一个非 completed 节点开始执行**；
- 不允许跳过一个未完成节点去跑后面的节点（业务串行链，见任务书 5.1）；
- 重跑已完成节点须显式参数 `--force-node <name>`，且旧产物先移入 `archive/`（禁止原地覆盖——留痕红线）。

### 1.3 失败与降级的流转

```
节点执行失败 → 状态回 pending，state.json 记录 error（code 见第四章）
  → 自动重试（仅 LLM 调用类失败，见第三章）耗尽
  → 置 manual_intervention + 降级清单记入 state.json（D1：按人工介入计入，分母不缩减）
  → 后续节点继续自动推进（降级节点视同已处理，不阻塞下游）
  → 人工修复后可显式重新触发该节点（正常续跑路径，无特权通道）
```

### 1.4 用户主动停止

Web 停止操作只取消当前后台协程，不删除已落盘且已校验的产物。协程完全收敛后，仍为
`running` 的节点回退为 `pending`，并记录 `X-ORCH-04`；用户可从该节点或通过全量重跑
继续。服务重启时不存在可恢复的内存协程，启动阶段同样将遗留 `running` 节点回退为
`pending`。停止不是 `completed`，也不记为 `manual_intervention`，避免跳过尚未完成的下游节点。

- **testcase_generate 特例**：脚本编译失败（`loadable=false`）不算节点失败，照常产出 `testcases.json`，失败明细如实记录，由 auto_execute 执行时跳过并计数——不静默、不阻塞；
- **code_scan 特例**：`empty`（X-CODE-02）是正常态，流程继续；`error`（X-CODE-01）才是失败；
- 状态持久化只写一个文件：`<job_id>/state.json`（节点状态 + 错误 + 降级清单 + 人工标注字段），编排崩溃后从中恢复。

## 二、产物目录布局与文件命名（三人共同遵守）

```
/data/llm-autotest/<job_id>/
├── state.json                 # 编排状态（甲独写）
├── requirement_items.json     # 甲写：9 个产物文件名 = schemas/ 下的 Schema 文件名
├── code_inventory.json        # 乙写：一一对应，不自造别名
├── interface_candidates.json  # 乙写
├── interfaces.json            # 甲写
├── review_mapping.json        # 甲写
├── testcases.json             # 丙写
├── execution.json             # 丙写（test-executor 写入，orchestrator 只读）
├── defects.json               # 丙写
├── regression_index.json      # 丙写
├── metrics.json               # 甲写（程序化汇总，不经 LLM）
├── test_report.md             # 甲写（最终报告）
├── scripts/                   # 丙写：生成的 pytest 脚本（testcases.json 的 script_path 指向此处，相对 job 根目录）
├── fixtures/                  # 丙写：D8 前置数据（流程启动前预置）
├── llm_calls.jsonl            # 甲写：LLM 调用留痕（追加型，见第三章）
├── logs/                      # 各服务写自己日志：<service>.log
└── archive/                   # --force-node 重跑时的旧产物归档
```

- **写入权限是排他的**：每个产物只有一个写方（上表已标），其余服务/前端只读——这是三人互不冲突的物理保证；
- 开发环境产物卷本地路径由 [config.py](../services/orchestrator/src/orchestrator/config.py) 的 Settings 提供，容器内统一挂 `/data/llm-autotest`；
- 假数据样例（`schemas/samples/*.sample.json`）仅用于 Day 1–3 开发，**禁止混入产物卷**。

## 三、LLM 调用治理（甲实现，红线落地细则）

- **留痕**：每次调用向 `llm_calls.jsonl` 追加一行：`{call_id, timestamp, node, prompt_file, prompt_version, sampling, input_digest, output_digest, duration_ms, tokens, ok}`；`call_id` 格式 `LLM-<job_id 短码>-<序号>`；
- **超时**：默认 300s（`LLM_TIMEOUT_S` 可配）；考虑 MiniMax 推理批次的实际耗时，超时算调用失败；
- **重试**：仅网络类/超时类失败重试，最多 2 次、指数退避（5s/20s）；**Schema 校验失败不重试**（重试同样会失败，直接节点失败——校验失败是 Prompt 或模型问题，走人工介入，不许截取可用部分）；
- **Prompt 一致性**：`prompt_file + prompt_version` 必须出现在留痕里且与 [prompts/](../prompts/) 目录实际文件对应——禁止内联 Prompt 字符串（红线，`.rules/llm-integrity.md`）；
- **成本口径**：token 数从 API 响应取原始值，不做任何换算修饰。

## 四、错误码总表（三人分段命名，禁止自造格式）

错误结构统一 `{code, message, node_id?, details}`（契约与任务书 5.4 已冻结）。code 取值按**泳道分段**：

| 段 | 归属 | 已定义 | 含义 |
|----|------|--------|------|
| `X-CODE-01` | 乙 | ✅ 契约已定 | 仓库路径不存在等硬错误 |
| `X-CODE-02` | 乙 | ✅ | 仓库无可分析内容（正常态，流程继续） |
| `X-CODE-03` | 乙 | ✅ | 超大仓库截断 |
| `X-LLM-01` | 甲 | 本文新增 | LLM 调用超时/网络失败（可重试） |
| `X-LLM-02` | 甲 | 本文新增 | LLM 输出未过 Schema 校验（不重试，人工介入） |
| `X-LLM-03` | 甲 | 本文新增 | Prompt 文件缺失/版本不匹配（配置错误，人工介入） |
| `X-ORCH-01` | 甲 | 本文新增 | 产物校验失败（下游读到不合规产物） |
| `X-ORCH-02` | 甲 | 本文新增 | 断点续跑跳序请求（请求跑未完成节点的后续节点） |
| `X-ORCH-03` | 甲 | v1.1 新增 | java-parser 服务不可达/通信失败（含超时轮询耗尽；可重试由编排层决定） |
| `X-ORCH-04` | 甲 | v1.2 新增 | 用户主动停止或服务重启中断任务；当前节点安全回退为待运行，可续跑 |
| `X-EXEC-01` | 丙 | 本文新增 | 脚本不可加载（loadable=false 的执行侧对应） |
| `X-EXEC-02` | 丙 | 本文新增 | fixtures 缺失（D8 前置数据未预置） |

新增错误码的唯一途径：提交 MR 修改本表 + 相应 Schema/契约同步升版——禁止代码里直接出现表外字符串。
