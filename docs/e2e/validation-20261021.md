# E2E 重构技术验证记录

日期：2026-10-21。范围：本机技术链路，不是客户业务系统验收。

## 环境与模型

- 主服务使用标准 `.local-artifacts/jobs`，用户原任务已完成九节点后才重启。
- 技术验证使用独立后端 8002、前端 5174；任务 `job-e2e-refactor-validation`。
- 公司任务模型 `deepseek-chat`，经公司配置网关调用。场景设计、用例生成、复核及必要的重新定位均调用任务客户端，没有用 Codex 自身替代业务分析模型。
- 真实页面中的唯一控件名称与下拉选项匹配由程序完成，避免模型重复转换机械格式；公司模型仍负责业务场景和预期。
- 空任务 `job-e2e-target-empty` 用作只读目标，避免验证运行本身产生报告后污染“目标任务没有执行记录”的前置条件。

## 已确认的链路

公司模型生成的场景：进入 E2E 工作台、选择空任务、检查页签、切换执行报告、核对“尚无 E2E 执行记录。”。

- 第一次完整通过：10 步操作和检查，6 条断言，证据完整。
- 相同用例快照重复通过后，自动保存一条回归资产。
- 从回归资产入口执行不可变快照再次通过；回归原用例编号和版本保持不变，累计三个真实通过批次。
- 每批次保存 46 个证据文件，包括每步前后截图、页面状态、网络、控制台和结果。
- 离线报告的 86 个文件引用经文件存在性核对全部可用。
- 在浏览器工作台展开通过用例及末步断言，预期、实际、前后截图可见。

以上数字对应已完成的单用例快照验证，不能解释为所有需求或所有客户业务场景通过。

## 修正的问题

- 非必需报告尚未生成的 404 不再使整个工作台配置和设计加载失败。
- 不因缺少独立 target_intent 而丢掉已有明确 intent 的步骤。
- 省略的单规则绑定元数据可由程序确定；不能由此修改业务预期。
- 下拉选项适配核对真实 options 与原意图，保留模型原返回。
- 弱模型把页签预期改成侧栏名称的输出不再直接进入有效设计；固定文本预期来自需求原文。
- 尚未调用实际断言就阻断的步骤不计作已执行断言。
- 控件属性尽量完整分组，同份观察由原 15 页降为 5 页，所有字段仍保留。
- 多个历史用例共用显示 ID 时按快照区分复测；其他步骤提前失败不等同于原缺陷复验失败。
- 原生下拉和页面反馈文本可以确定匹配时直接定位，避免所有机械步骤都调用模型。
