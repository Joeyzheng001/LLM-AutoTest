## 范围

分析和验证被测接口自身的输入校验、下游结果处理、返回转换及异常处理。下游只作为本接口的输入边界，不审查下游内部业务实现。

测试设计的准入条件是本接口处理逻辑和预期具有源码证据。当前环境是否能够产生指定返回，不作为删除设计的理由。

## 逐项确认的优化清单

1. 请求体为 null 与 accountNo 为空字符串必须拆成两个独立用例。前者验证 HTTP 请求体绑定边界，后者验证本接口的账户号必填处理；不能合并后因框架提前拦截而将两个场景一起排除。生成器负责分别整理预期，不能把内部的分析限制转嫁给使用者。此项已确认，待统一实施。
2. O32 返回 null 的兜底场景必须稳定绑定本接口的 o32TrialObj 空值分支。原文及接口归属已能确认时，程序应整理引用列表，不能因模型遗漏 evidence_refs 中的编号而丢弃设计；下层 executorResult 的空值/异常处理与本接口对象为空不得混为同一分支。区分真正缺少处理源码、引用列表缺项以及执行条件未准备，诊断应反映最终问题。此项已确认，待统一实施。

排查记录：最近一轮 IF-REST-001 的 O32 null 兜底候选并非没有源码。初次及最后一次修复输出引用了 EVD-0071 的 executorResult 空值/异常条件，该原文在输入中存在，但未列入候选的 evidence_refs；中间修复曾改为 EVD-0011 的 o32TrialObj 空值条件，又缺少请求前置条件的引文。最终提示没有区分引用列表缺项、修复中的分支切换和真正源码缺失，需在后续优化中分别处理。

正常返回场景的当前分析：LLM-precodet-1431 将第一个请求条件写为 param.accountNo exists，却未提供该条件引文；LLM-precodet-1432 补上了 EVD-0015 的账户号空白校验原文，原文确实存在，但 evidence_refs 仍只包含 EVD-0011、EVD-0052、EVD-0071，遗漏 EVD-0015，导致再次拒绝。此外字段存在不足以通过 StringUtils.isBlank 校验；正常请求应明确账户号不为 null、空字符串或纯空白。正常条件可以从失败校验的相反路径推导，应保留推导依据并由程序整理引用，不因辅助引用列表遗漏删除正常用例。此项为当前分析结论，待用户逐项确认。

### 其余提示逐项分析（待统一实施）

- IF-REST-002 请求体为 null：同第一项，生成独立的 HTTP 请求体绑定边界用例；不能引用未被调用的 Service null 分支，也不能因此删除这个请求场景。
- IF-REST-002 自动审批阶段非法、ExDestination 非法、标准服务返回空结果：LLM-precodet-1434 至 1440 的实际返回均遗漏 assertions 键，已有 expected_behavior，因此触发“oracle 字段与输出契约不一致”。这是内部数据结构遗漏，不能描述成接口场景无效。针对无响应体字段断言但已有源码处理行为的设计，程序可以补全 assertions=[]；HTTP 映射未确认应单独标注。不能给没有业务预期的正常用例用空数组凑通过。
- IF-REST-003 riskChannel=0：LLM-precodet-1444、1445 引用了 EVD-0063 的配置空集合检查原文，原文在输入中存在，但 evidence_refs 没有该编号。配置非空是空集合失败分支的反向前提。应整理实际有效引用，保留基于已有配置执行全部通道的用例；普通配置存在不能自动升级为修改配置的控制夹具要求。
- IF-REST-004 有效 code 正常执行：LLM-precodet-1451、1453、1454 的 assertions=[]，expected_behavior 也未提供，只有 HTTP 200；这是真正的响应预期分析不充分。应继续分析对应服务的返回结构和本接口的转发、映射关系；动态结果可写字段关系或透传预期，不要求编造固定业务值。正常场景需保留；未补齐机器断言时明确记录，不应删除，也不能只凭 HTTP 200 声称业务已验证。
- 两条 38 条 P0-oracle：同一批校验不通过用例的两次汇总，不能按 76 条问题呈现。原始生成中存在大量正常/边界场景绑定异常类别 oracle 的情况，源于正常预期未保留后仍按需求维度补产。应先补齐对应业务预期，再绑定生成用例，合并重复诊断并报告具体不匹配项。
- 6 个需求测试点未关联设计：属于上游排除后的覆盖缺口统计，不是新的接口异常条件。修复上游后重新计算；需求覆盖还必须核对用例的输入和断言是否真的验证该规则，仅挂 testpoint_id 不能算覆盖。
- F-GEN-05 的 15 个“展开不足”：当前程序按 ceil(case_split_hints 数量 × 0.6) 计算期望用例数，例如 5 个建议维度要求至少 3 条。维度由模型建议，60% 是程序设定，不是接口契约或需求给出的用例下限。应以确实不同的业务条件与预期结果核对覆盖，取消机械条数门槛及因此触发的凑数补产。重复或没有源码/需求依据的建议维度应合并或移除，而不是要求使用者人工解释数量。

## 条件与执行准备

| 字段 | 含义 |
| --- | --- |
| `preconditions` / 用例 `request_conditions` | HTTP 请求自身必须满足的参数条件 |
| `state_conditions` | 本接口使用的下游返回、应用配置、服务注册状态或测试数据条件，附本接口源码原文 |
| `state_conditions[].mode=integration` | 正常联调前提，使用真实环境执行，不要求安装控制夹具 |
| `state_conditions[].mode=controlled` | 需要制造特定返回或环境状态，执行前检查对应准备能力 |
| `branch_outcome` | 目标 if 条件成立或不成立，避免把 null 兜底路径与正常返回混为一谈 |
| `execution_readiness` | 设计时的准备情况：ready、conditional、blocked；执行时重新检查 |
| `execution_blockers` | 未补齐有效请求、未准备测试记录等阻塞原因 |
| `oracle_basis=integration_entry` | 公司模型生成的普通有效入口检查，只验证 HTTP/结构，不绑定内部 if 分支或 Claim 覆盖 |
| `execution_state` | 已执行、未执行、已请求待判定、复用实际响应核对分别统计 |
| `expected_behavior` | 本接口抛出异常、兜底或返回的具体行为及源码引文 |

当本接口处理行为已经明确，但 HTTP 包装/异常映射源码未取得时，使用 `expected_status=unresolved` 保存设计与 `expected_behavior`，有确定请求输入且没有其它环境阻断时，执行器可以发送请求收集响应，但不判定通过或缺陷；有控制状态或数据缺口时仍不发送。不能猜 HTTP 500，也不能因为 HTTP 映射未知就删除本接口处理行为的测试设计。

普通下游成功与服务正常注册可以作为真实环境的联调前提。特定的 null、错误返回、空配置或注册项缺失即使被接口正常处理，也属于需要指定状态的场景。

未准备指定状态的设计保留在 `testcases.json`，执行结果记录跳过及原因，不计为通过。生成器按每个 oracle 检查漏产并定向补充；模型仍无法给出有效请求时保留条件与预期，明确禁止发送占位请求。

执行器从 Code Review 契约重新读取控制要求，不能通过删除用例上的状态字段绕过检查。单条用例条件不满足，不影响其它用例。

## 证据与结论

预期及固定值继续校验接口归属、源码原文和字面值；环境不可控不再被误记成响应预期无依据。

动态字段存在性断言可以验证响应结构，但不能单凭结构断言宣称内部业务分支已命中。实际响应不自动成为业务正确性的标准。

报告逐接口列出正常场景设计数、执行数、通过数和未执行数。没有通过正常场景的接口明确标记正常业务验证未完成，不能用异常请求的通过率替代该结论。
