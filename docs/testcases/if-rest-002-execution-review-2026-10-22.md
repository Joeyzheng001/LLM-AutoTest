## 从源码评审到报告的改进顺序

1. **Code Review 明确断言能证明什么。** `integration_entry` 场景命名为入口可达检查；源码分支的前序条件、可控制的下游返回、可观察字段要分开记录。TC-015 不应只写“O32 错误码为 0”，还要写出有效风控序号和审批处理异常的触发条件。TC-010/011 的通用 9999 映射不能由业务异常代码自行推定。
2. **用例生成先检查可达性。** 业务成功请求需具备执行器所需字段与有效取值，并为 `icmTrialObj`、`o32TrialObj` 配置成功断言。依赖特定服务返回或抛异常的场景，在 fixture 缺失时保留设计并标注未就绪，不把普通请求当成已覆盖该路径。
3. **执行结果保留证据层次。** 对直接请求、响应复用、未执行、已请求待判定分开统计；对复用响应只核对字段，不声称重新执行了场景。分支未触达时保持待判定，避免将实际 O32 400 判成 TC-015 的产品失败。
4. **报告和界面表达验证范围。** 区分“HTTP 符合”“结构符合”“业务断言符合”“复用字段符合”；状态/结构符合而响应含业务错误码时显式提示。正常业务覆盖率仅由直接请求且业务断言符合的用例贡献。
5. **环境响应契约按范围保存。** 零字节与 JSON `null` 是两种独立输入；当前任务 `required_body_contract=null`。若将既有人工确认用于本接口，应绑定该网关、接口和环境，不扩展为所有异常的统一预期。

本次已修改报告生成与界面展示，落实第 1 点的入口命名及第 3、4 点的统计和提示。历史执行文件保留原样；新报告格式在后续生成时生效。

## 10:48–10:55 最近一轮运行复核

本轮共有 36 条用例：直接请求且现有断言符合 9 条，复用响应符合 2 条，已请求但响应契约待确认 12 条，未执行 13 条。仅 1 条直接请求达到业务断言符合。IF-REST-002 形成 7 条最终 oracle、8 条用例：TC-009 是入口结构符合，TC-013 是 STD 路径的 O32 空结果断言符合，TC-014 复用 TC-009 的响应核对字段，TC-010/011/015/016 已请求但待判，TC-012 未执行。TC-015/016 现为零字节和 JSON `null` 请求体，上一轮的审批信息异常用例没有进入本轮最终设计。

本轮 Code Review 有一处明确误判。`RiskApprovalServiceImpl.trial` 在 `processApprovalInfo` 抛异常时进入本地 `catch`，设置 O32 `ErrorCode=9999` 和两个空列表，随后 `return response`；控制器也正常返回该对象。模型曾给出这一源码路径，但分支目录原先只抽取 Controller 的 `catch`，而 HTTP 200 校验只查 Controller 的 `catch`，导致 Service 兜底被写成“已自动修复并通过源码校验”后又从最终预期中删除。已加入“被调方法 catch 后正常 return”的静态候选，并让 HTTP 200 校验识别这条本地兜底路径；异常如何稳定触发仍须追踪到可控输入或夹具，不能因此直接判为可执行。

报告的“32 个源码场景、32 个已绑定设计”只包含最终准入的 oracle，不包含被隔离候选和静态分支目录。旧目录有 108 处候选，其中多处来自重叠源码证据；不能将“未关联”直接换算成漏掉的 HTTP 用例。后续报告已改为“最终准入的源码预期”，并明确分母范围。另将 O32 空结果已保留设计的诊断归为系统已处理，避免把正向处理记录误标为“无效候选”。

仍待优化的执行准备按影响排序：先为常规请求准备能得到有效业务结果的样本，并将入口结构检查与业务成功检查分别统计；为 13 条未执行场景逐条绑定真实可用的控制夹具与触发条件；将已经讨论确认的空请求体网关响应按接口及环境写入 `required_body_contract`（本轮任务配置仍为 `null`），同时保留“通用 9999 无法单独证明具体异常发生”的判断；对 12 条已请求待判场景补异常映射或可观察的调用证据。上述新源码判断需要新一轮 Code Review 才会写入产物，历史报告不回填。
