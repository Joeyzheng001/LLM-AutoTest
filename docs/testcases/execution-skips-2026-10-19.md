## 已确定的问题及处理

1. 已收到 HTTP 200 的四条框架请求不能叫“未执行”。它们与 Spring 默认 400 的差异需要核对项目/网关包装，只记录响应，不据此反写预期。
2. TC-002（空账户号）、TC-016（不支持的市场）、TC-038（未知路径枚举）具有请求可控的输入，主要缺口只是异常映射。允许发送并保留响应，标为“响应契约待确认”，不算断言通过或产品缺陷。
3. TC-012 的 O32 非零错误码条件已经出现在 TC-014 的真实响应里。只在源码直接字段映射和前序条件都能核对时，复用该响应检查原有断言，记录 source_case_id 和实际请求参数，不另造预期。TC-005 同理可以观察返回的错误码；其当前断言主要是编号回显，仍不算业务验证。
4. TC-013 不能因为返回 riskOutList=null 就认定进入了“无风控序号”路径：O32 错误会提前返回，根本没有调用提取逻辑。未知或未触达路径保留待执行。
5. TC-003 误叠加 downstream_response：原分析把不同方法同名 executorType 的赋值混在一起传播。改为在各方法证据内追踪来源；注册表来源单独识别。
6. TC-006 需要控制明细处理器注册状态；TC-022、027 需要应用配置；TC-039 需要 Spring 服务注册表。外部 HTTP 响应不能证明这些内部状态已准备。
7. TC-004、010、011 的 Java 方法/对象为 null，以及 TC-024/032、026/034 的 null/Exception 兜底，不能仅凭外部错误码推断。这些设计保留，当前没有控制条件时如实列出具体缺口。
8. TC-014、015 不再把提前返回的空列表当作目标开关逻辑通过；TC-035、036 必须加强选中通道的结果断言后，才能作为业务规则检查。

## 执行和报告口径

- `executed`：实际执行并按已确认响应契约判定。
- `observed_unjudged`：已发送，响应映射待确认或目标路径未触达；不计入产品缺陷或通过。
- `not_executed`：未发送，展示所有已知阻断及缺少的控制能力。
- `reused_response`：复用相同接口已收到的真实响应核对另一条已有条件设计；记录来源，不额外计一次 HTTP 请求，不把原场景脚本直接归档为已独立执行的回归脚本。

这里只观察本接口收到的边界状态及其响应，不要求分析下游业务实现。无法从响应核验的内部条件不会被自动改写成已满足。

## 真实重跑中追加修复

- Java 引文中，换行/缩进以及相邻字符串常量拼接允许按词法等价绑定回原始源码片段；最终存储的仍是逐字存在的原文，不允许变量名、操作符或字面量内容变化。
- 透传失败路径不能引用另一个 error() 工厂的固定错误码。第一轮内部模型曾错误套用 9999，导致复用真实 400 响应时出现假失败；该候选需要修复，不能作为产品缺陷。
- 增加由公司模型产出的 integration_entry 普通入口检查，与具体 if 分支设计分开。只验证已有 HTTP/响应结构契约，不计内部业务分支覆盖，避免所有详细场景都要求控制状态时没有正常请求发送。

- 修复普通入口被空分支编号误拦：模型已经给出 normal 场景、HTTP/结构断言和有效请求，但 branch_id="" 不应被当作业务分支。程序将此类无控制要求的检查归为 integration_entry，清除空分支元数据和业务覆盖声明；四个接口原始回答回放均恢复了普通入口设计。
- 支持 in/not_in 有限集合条件；缺少请求条件引用时，仅在能唯一定位读取该请求字段的方法时绑定完整原文，保留前序判断，不要求模型重复抄写代码。
- 修复后续异常触发检查遗漏 in/not_in：公司模型原始回答 `LLM-precodet-2189` 已给出 code 不属于完整枚举集合的前提，解析器通过后却因场景标题包含“抛出异常”被误判无请求可控条件。现在保留该设计，未知 HTTP 映射仅作为观测待判定，不再当作环境状态缺口。
- 当公司模型的响应断言修复仍失败或返回空设计时，尝试保留原来的源码分支设计：仅移除不成立的响应断言，再由严格解析器重新核对分支、请求/状态条件、逐项引文和 HTTP 状态依据。只有全部通过才保留为 pending_expectation，增加不可过滤的执行阻断，清空业务覆盖声明；不会自动补预期或将其作为 HTTP 通过。源码分支、条件本身无证据时仍不能保留。
