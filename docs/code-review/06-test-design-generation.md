# 06 接口测试设计生成

[返回目录](README.md) · [上一步](05-interface-evidence-and-branches.md) · [下一步：校验与修复](07-validation-and-repair.md)

## 目的与分工

让 LLM 根据本接口源码提出测试场景与预期。程序负责整理输入、提供分支目录、安排补查及合并候选。模型输出先是候选，只有通过步骤 07 才成为有效设计。

## 输入与输出

每个接口的输入包含：接口定义、完整可用证据、分支目录、需求 Claim、当前可用的控制夹具摘要。

模型返回 `{"oracles": [...]}`；每条设计的主要字段如下：

| 字段 | 含义 |
| --- | --- |
| interface_id / scenario / category | 对应接口、场景和类型 |
| branch_id / branch_outcome | 目标条件及成立/不成立方向 |
| preconditions | HTTP 请求可设置的前提 |
| state_conditions | 下游、配置、注册表、测试数据等前提 |
| expected_status | 已知 HTTP 状态、状态类别或 unresolved |
| assertions | 可由执行器判断的响应断言 |
| expected_behavior | 有源码引用的行为说明，可用于尚未形成断言的设计 |
| evidence_refs / evidence_quotes | 证据编号与逐项原文 |
| covered_claim_ids | 设计声称覆盖的需求声明，后续受程序限制 |

## 当前处理过程

1. 按接口组织证据，排除标记为不完整的片段，并对完全相同的证据条目去重。
2. 为该接口补入分支目录，以一接口一批方式调用测试设计提示词。
3. 解析候选；一条坏候选不应让同接口其他有效候选一起丢失。
4. 对未被确定性设计替代的失败候选，逐条预检查并定向请求修复。
5. 当普通正常设计不足时，单独请求模型补充普通有效请求的入口设计。
6. 对部分请求可选择、但目前只有结构断言的正常分支，再逐分支请求业务断言补查。
7. 对相同接口、类别、分支方向、请求条件和状态条件的候选，按断言强度选择，避免仅改名重复。
8. 追加适用的程序推导设计，包括必填请求体边界、部分 DTO 校验、空白字段校验等。
9. 整理控制要求、执行缺口和编号，形成 `test_oracles`。

程序推导只适用于实现中明确支持的源码模式，并非所有框架行为或业务异常都能自动推导。

## 接口间并行（2026-10-20）

测试设计阶段在 Claim 汇总和补充证据完成之后开始，最多同时处理 `CODE_REVIEW_MAX_CONCURRENCY` 个接口（默认 4）。每接口独立保存候选、解析闭包、修复列表、告警和连接失败记录。同接口的初次生成、逐条修复、普通入口补查、请求分支补查仍按依赖串行执行。

按原始接口顺序收集合并候选、告警与连接错误，再统一补充确定性设计和分配 oracle 编号。某接口发生核心网络错误，仍使整个预期提取失败，不会把其他接口完成当作本轮完整成功。

## 普通入口与业务分支

普通入口使用 `oracle_basis=integration_entry`，不填写业务分支编号，允许验证已确认的 HTTP 状态、响应字段或请求编号回显。

直接透传 Object、没有承诺业务字段的普通入口，可以保留有源码依据的 HTTP 状态检查和空 assertions。此时 assertion_scope=status_only，不因缺少业务字段断言删除正常请求，不算业务需求覆盖。只有该普通入口的 HTTP 状态已确认且没有控制条件时才适用；其它业务分支、未知 HTTP 映射仍按原规则处理。

2026-10-20 起，也允许本控制器直接写入实际返回对象的固定字段。程序核对 setter 的真实字面值、普通路径上的赋值位置及返回对象；只在 catch 或条件块中赋值、被后续普通路径重写、无法确认来源的固定值不会因此获准。入口设计仍清空 covered_claim_ids，不能冒充内部 if 的需求覆盖。

入口补查按最终候选及适用的程序成功设计判断：已有有效普通入口时，不再因为它只有结构断言而重复要求一份 business 入口。正常请求存在与业务断言完整性分别判断。

程序会把符合条件的普通 normal 候选归为入口设计，清除空分支元数据和业务覆盖声明，减少弱模型遗漏内部标记造成的误拦。带有真实目标分支的设计仍需要独立证明条件与处理行为。

缺少控制能力不应成为删除源码设计的理由。需要指定空值/错误返回的场景保留为条件化设计，当前能否执行在步骤 08 判断。

## 示例

审批试算接口至少需要分别考虑普通有效请求、缺失请求体、自动审批阶段非法、下游空值和下游错误处理。普通请求不要求先制造下游 null；null 兜底也不能被普通入口的 HTTP 200 替代。

## 失败处理与限制

- 连接失败不是“没有业务设计”：记录受影响接口并使本轮核心预期提取失败，避免写出貌似完整的评审。
- 单个候选断言失败：先修复；仍失败时按步骤 07 判断能否保留待补设计。
- 正常入口补查和部分业务补查会增加模型调用，不是每接口只调用一次。
- 去重按条件和源码定位，不是按场景标题，也不是实际 HTTP 请求去重。
- 尚无保证每个源码分支都产出设计的全量对账机制。
