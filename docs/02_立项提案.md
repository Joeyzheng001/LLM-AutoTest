# 立项提案：LLM-AutoTest

- **提案日期**：2026-09-14
- **依据文档**：[01_需求澄清记录.md](01_需求澄清记录.md)
- **项目周期**：一周（首个可用版本冲刺）
- **执行团队**：新组建专项小组（多角色协作）；人力配置假设 4 人全时投入（1 名测试架构师兼 LLM 工程、2 名测试开发、1 名测试工程师，详见「六、一周排期计划」）

---

## 一、背景

当前接口测试面临三个核心痛点：

1. **接口文档缺失**：团队 Java 多仓库体系下无统一接口文档（无 Swagger/OpenAPI 等），测试用例编写依赖人工阅读代码，效率低且易遗漏。
2. **无沉淀资产**：无历史测试用例、无历史缺陷数据，测试工作每次从零开始，无法复用，回归成本高。
3. **LLM 能力未被利用**：团队已具备 Prompt Engineering / LLM API 调用能力，且公司现有 GLM-5.3 可直接使用，但尚未在接口测试领域形成系统性实践路径。

行业趋势上，LLM 在代码理解、用例生成、测试执行编排等环节已展现出可行性，但缺少一条"从需求输入到回归沉淀"的端到端实践路径验证。本项目以一周冲刺交付首个可用版本，验证该路径在本团队环境下的可行性，为后续规模化投入提供决策依据。

## 二、目标（可量化）

| # | 目标 | 量化指标 | 验证方式 |
|---|------|----------|----------|
| G1 | 交付可运行的系统 | 覆盖 5 种协议（REST/gRPC/GraphQL/SOAP/MQ）× 6 环节闭环（Code Review → 自动执行 → 测试报告 → 缺陷清单 → 复测 → 回归沉淀），每个环节至少 1 个场景跑通。「跑通」最低判定标准：① 环节端到端执行完成；② 产出结构化产物；③ 断言结论为通过/失败二态明确。仅「脚本生成成功 + Mock 执行演示」的降级场景不计入「跑通」，在报告中单独标注为「路径演示」 | 验收日现场演示 |
| G2 | 需求文档解析 | 支持 Word / Markdown / Excel 3 种格式输入，各格式至少 1 份样例文档解析成功 | 解析产物抽查 |
| G3 | 接口逆向解析 | 对指定 Java 多仓库（≥2 个仓库）完成代码扫描与接口还原，接口还原产出结构化清单。兜底演示仓库的还原结果单独标注，不计入 G3 达成，报告中与真实仓库结果分列呈现 | 还原结果人工抽查（真实仓库/兜底仓库结果分列核对） |
| G4 | Code Review 三视图 | 风险清单、遗漏功能清单、逐条需求-代码映射表 3 种产出全部生成（一次生成、三种视图） | 产物完整性检查 |
| G5 | 自动化率实测 | 完成"无人工操作节点数 / 总节点数"的度量方案设计（9 节点口径），并在验收演示中实测出第一个数值，按判读框架解读：≥70% 为高（建议推进规模化投入）/ 30–70% 为中等（按瓶颈节点选择性投入）/ <30% 为低（瓶颈节点治理为规模化前置条件） | 度量报告 |
| G6 | 周期约束 | 一周内完成全部交付 | 里程碑检查（对照「六、一周排期计划」逐日核对交付物） |

**G1 为核心目标，G6 为刚性约束，G2–G5 为验收细节。**

## 三、范围（MVP 做什么）

MVP = 全功能首个可用版本，各环节可深可浅，以"跑通"为标准；生产成熟度按后续迭代推进。

### 输入通道

- 需求文档输入：Word / Markdown / Excel 三格式解析
- 代码输入：Java 多仓库扫描，LLM 逆向解析接口（唯一接口来源，无文档依赖）

### 处理流水线（6 环节闭环）

1. Code Review：对照需求文档核查代码实现，产出映射表 + 风险清单 + 遗漏功能清单
2. 用例生成：基于还原的接口与需求生成可执行测试脚本
3. 自动执行：脚本无人工干预执行
4. 测试报告：自动输出执行报告
5. 缺陷清单：自动输出缺陷清单（本地缺陷记录文件，不对接 Jira 等缺陷管理系统，见非目标 N9），支持复测流程
6. 回归沉淀：通过的脚本沉淀为回归自动化脚本资产

### 度量体系

- 9 节点口径定义（需求解析、代码扫描、接口还原、用例生成、执行、报告、缺陷提交、复测、回归沉淀）
- 验收演示中实测一次自动化率数值

### 技术基线

- LLM：现有 GLM-5.3，不新增模型投入
- 测试框架：无存量约束，项目内选型并给出选型理由

### 组织形式

- 新组建专项小组执行，多角色协作（用例模板维护 / LLM 生成执行 / 人工审核）；人力假设 4 人全时投入，P1 用户故事统一按最小可用实现（每卡片 1 个最小场景），以匹配一周容量（对应评审 TA-01）

## 四、非目标（明确不做什么）

| # | 非目标 | 说明 |
|---|--------|------|
| N1 | 首版不做生产级成熟度打磨 | 首版各环节跑通即可，稳定性、性能、大规模并发按迭代计划推进 |
| N2 | 不做 UI 测试 / 性能测试 / 安全测试 | 严格限定在接口测试自动化范围 |
| N3 | 不做 LLM 训练 / 微调 | 仅使用现有 GLM-5.3 的推理能力 |
| N4 | 不做幻觉问题的系统性应对 | LLM 幻觉（虚构接口、错误参数类型等）的治理方案不在本次范围 |
| N5 | 不做接口文档治理 | 不输出或维护 Swagger/OpenAPI 文档，仅做临时的接口还原结构化清单 |
| N6 | 不做合规 / 安全审查建设 | 已确认无合规要求、无敏感信息、无审查流程需求 |
| N7 | 不做历史数据资产建设 | 无历史用例、无缺陷库，不回补此类资产 |
| N8 | 不做跨团队推广 | 产出仅面向测试团队内部，不涉及其他团队的方法论推广 |
| N9 | 不做缺陷管理系统对接 | 本项目内"缺陷提交"仅生成本地缺陷记录文件（见 PM-03 澄清）；与 Jira 等缺陷系统的对接列入规模化阶段评估 |
| N10 | 不做需求变更的增量处理 | 不做需求文档更新后映射表与用例的增量刷新；输入变更即整体重跑对应节点（断点续跑见规格 F-ORCH-02） |

## 五、风险清单

| # | 风险 | 影响 | 概率 | 应对策略 |
|---|------|------|------|----------|
| R1 | **范围与周期严重不匹配**：5 协议 × 6 环节 × 一周，范围远超常规首版容量 | 高：验收日部分环节无法跑通，项目目标落空 | 高 | 严格执行"跑通"标准：每环节 1 个最小场景即可；第 2 天末做范围检查点，未跑通环节降级为"路径演示 + 界面演示"，砍深度保广度 |
| R2 | **Java 多仓接口逆向解析失败或质量过低**：无接口文档，LLM 从代码还原接口是全新能力，复杂框架代码（Dubbo/gRPC/自定义注解）解析可能失败 | 高：下游全部环节（用例生成、执行）无输入 | 中 | 优先级最高，安排在 Day 1–2 攻坚；准备 1 个代码结构简单的演示仓库兜底，兜底仓库结果单独标注、不计入 G3 达成，报告中与真实仓库结果分列，避免呈现虚假正向结论；接受还原产物人工抽查后修正 |
| R3 | **gRPC / GraphQL / SOAP / MQ 执行环境不可用**：多协议被测服务依赖部署环境，一周内未必能备齐 | 中：对应协议环节验收失败 | 中 | 演示环境优先级排序：REST > gRPC > GraphQL > SOAP/MQ；难部署协议降级为"脚本生成演示 + Mock 服务执行" |
| R4 | **GLM-5.3 生成质量不稳定**：无 Few-shot 样本，用例生成与 Code Review 产出质量波动大 | 中：产物可信度受损 | 中 | 固化 Prompt 模板版本；验收前完整彩排 1 次，锁定演示输入 |
| R5 | **自动化率首次实测数值过低**：9 节点中人工介入节点多，实测结果不具说服力 | 中：影响项目结论与后续投入 | 中 | 提前管理预期：首版数值仅作基线，报告同时给出"瓶颈节点分析 + 优化路径" |
| R6 | **专项小组组建与多角色协作磨合**：新小组无既有分工默契，一周内协作开销占比高 | 低：进度延误 1–2 天 | 中 | Day 1 上午完成角色分工与接口约定（各环节输入输出格式），采用"各环节负责人 + 每日站会"轻量机制 |
| R7 | **复测与回归沉淀环节被挤压**：位于流水线末端，前置环节延期将直接压缩其时间 | 低：闭环不完整，G1 部分落空 | 中 | 复测与回归沉淀可基于 REST 单协议最小闭环先行准备，与前置环节解耦 |
| R8 | **GLM-5.3 token 成本与限流未评估**：多仓源码 + 需求文档 + 映射比对全部送入 LLM，token 消耗量级未估算；内部网关若有限流，Day 1–2 逆向攻坚可能被限流阻塞而非被技术阻塞 | 中：攻坚进度受阻、调用成本不可控 | 中 | Day 1 完成 token 用量级估算并向网关确认配额/限流策略；采用静态特征定位优先、按接口分块送入的策略压缩送入量（见规格 R-REV-02/R-REV-04）；调用配额优先保障接口逆向攻坚环节 |

**风险总评**：R1 与 R2 为本项目两大关键风险，均已有应对策略；整体风险可控，但需严格执行范围检查点机制。

## 六、一周排期计划（G6 里程碑，对应评审 PM-08/TE-09）

人力配置假设：4 人全时投入，分工如下（一人可兼多卡）：

- **A（测试架构师兼 LLM 工程）**：接口逆向解析（E-CODE-02）+ 上下文管理策略设计
- **B（测试开发）**：需求解析（E-REQ-01）+ Code Review 三视图（E-REVIEW-01/02）
- **C（测试开发）**：测试框架选型与执行引擎（E-TEST-02/03）+ Mock 服务 + 前置数据/鉴权配置
- **D（测试工程师）**：报告/缺陷/回归沉淀（E-REPORT-*）+ 度量方案（E-METRIC-*）+ 演示编排与彩排

| 里程碑 | 时间 | 交付物 / 检查项 |
|--------|------|----------------|
| M0 环境与分工 | Day 1 | 角色分工与接口约定完成（R6）；演示仓库环境探测完成，含鉴权/前置数据识别（PM-02）；token 用量估算与配额确认（R8）；接口逆向攻坚启动 |
| M1 范围检查点 1 | Day 2 末 | 接口还原 ≥5 个接口（真实仓库优先，兜底预案就绪）；未跑通环节确定降级方案（E-METRIC-03 AC3） |
| M2 流水线中段 | Day 3 末 | 需求解析三格式跑通；Code Review 三视图产出；REST 用例生成 + 执行引擎可一键执行 |
| M3 闭环后段 | Day 4 末 | 报告/缺陷闭环/回归沉淀 REST 最小闭环完成；度量方案文档落地（F-MTR-01）；非 REST 协议按 R3 策略降级或就绪 |
| M4 彩排锁定 | Day 5 | 端到端彩排 ≥1 次，演示输入锁定（E-METRIC-03 AC1）；项目报告初稿（含自动化率实测演练） |
| M5 验收日 | 第 6 日上午 | 正式验收演示 + 自动化率首次实测（E-METRIC-02）+ 项目报告终稿 |

每日以站会同步进度；里程碑未达成时按 R1 应对策略执行范围裁剪（砍深度保广度）。
