## 一、产品经理评审意见

**评审维度**：场景有无遗漏、目标与范围是否一致

### 问题清单

**PM-01【场景遗漏】"人工审核"协作角色无对应 Story**
需求澄清记录 #4 明确协作模式为"用例模板维护 / LLM 生成执行 / 人工审核"三角色，但 14 张用户故事卡片中不存在任何"LLM 产物人工审核"环节的卡片——审核场景只以"人工介入节点"身份出现在度量模块。审核环节是谁、审什么、审核不通过如何回流，全部缺失。

**PM-02【场景遗漏】测试数据与前置依赖场景缺失**
接口测试普遍依赖登录态、鉴权 token、上游造数等前置条件。用例生成（E-TEST-01）与执行（E-TEST-03）的所有 AC 均未涉及前置数据准备场景。若演示仓库接口需要鉴权，执行环节将在 Day 3 之后才暴露此缺口。

**PM-03【场景遗漏】"缺陷提交"场景被静默降级为本地文件**
澄清记录 #6 与立项提案均使用"提交缺陷清单"表述，但功能规格 F-DEF-01 仅实现"失败用例 → 缺陷记录文件"，无任何缺陷管理系统（Jira 等）对接或对接计划。是刻意简化还是遗漏，未在文档中明示。

**PM-04【场景遗漏】需求变更的增量处理场景缺失**
规格仅有断点续跑（F-ORCH-02），没有"需求文档更新后如何增量刷新映射表与用例"的场景。虽然 PoC 可不做，但作为"实践路径研究"，变更响应是路径成立与否的核心场景之一，至少应在非目标中显式排除。

**PM-05【目标-范围不一致】G1 的"跑通"与降级口径存在张力**
G1 要求"每个环节至少 1 个演示场景跑通"，而 E-TEST-03 AC3 允许 SOAP/MQ 降级为"脚本生成成功 + Mock 执行演示"。降级后的环节是否计入 G1 达成，验收时必然产生争议，需在提案中预先定义"跑通"的最低判定标准。

**PM-06【目标-范围不一致】G3 的"指定仓库"口径可被兜底仓库架空**
G3 要求"对指定 Java 多仓库完成接口还原"，但 X-REV-04 允许接口数不足时"换用兜底演示仓库"。若最终演示基于兜底仓库，G3 实质未验证真实业务仓库，目标被架空。应规定：兜底仓库结果单独标注，不得计入 G3 达成。

**PM-07【目标不一致】G5 无判定基准**
评估标准为"无人工介入比例"，G5 仅要求"实测出一个数值"，未设定任何参考区间或解读框架（如 <30% / 30–70% / >70% 分别对应什么结论）。数值产出后无法直接支撑"是否值得规模化投入"的决策，削弱立项提案所述目的。

**PM-08【范围-资源不一致】一周排期计划缺失**
立项提案 G6 为刚性周期约束，验证方式为"里程碑检查"，但里程碑计划本身不存在——专项小组人数、并行度、每日交付物均未定义。E-METRIC-03 仅覆盖第 2 天范围检查点和彩排两个时点，不足构成排期。

## 二、技术架构师评审意见

**评审维度**：可实现性、技术风险、成本

### 问题清单

**TA-01【可实现性】一周容量与 11 模块 38 功能不匹配，且无人力假设**
按 14 张卡片（P0×7）估算，即便全部按演示级实现，一周需要至少 3–4 人全时投入且无返工余量。文档未给出小组人数假设，G6 的可行性无法评估。建议补充人力配置假设并砍掉 P1 卡片的实现深度。

**TA-02【可实现性】LLM 上下文管理策略未定义**
接口逆向（E-CODE-02）需要跨文件关联理解（Controller → Service → DTO、proto 与实现分离），GLM-5.3 单次上下文窗口有限。规格未定义分块策略、文件选择策略、跨文件信息传递方式——这是 R2 风险的技术根因，比"解析失败"本身更需要前置设计。

**TA-03【可实现性】"人工介入自动检测"的实现手段被低估**
R-ORCH-03 定义人工介入为"除启动命令外任何人工文件修改或命令干预"，F-ORCH-03 要求自动采集该标记。技术上需要文件监控/hash 比对 + 命令审计，一周 PoC 内实现可靠检测的成本不低。建议降级为"节点日志 + 事后人工标注"的半自动方案并如实计入自动化率。

**TA-04【技术风险】兜底仓库可能掩盖真实解析能力结论**
延续 PM-06：若逆向解析在真实仓库失败、在简化兜底仓库成功，预研报告将呈现虚假正向结论。建议在报告中强制分列"真实仓库解析成功率"与"兜底仓库演示结果"两组数据。

**TA-05【技术风险】Prompt 固化（R4 应对）缺少验证手段**
R-REQ-03 要求 Prompt 版本管理，但一周内没有时间建立 Prompt 变更的回归验证集。实际效果是"演示前锁定版本"（E-METRIC-03 AC1 已覆盖），版本管理本身可从范围中移除以减负。

**TA-06【成本】LLM 调用成本与限流完全未评估**
多仓库源码 + 需求文档 + 映射比对全部送入 GLM-5.3，token 消耗量级未估算；澄清阶段未提问预算与 token 配额/限流策略。若内部网关有限流，Day 1–2 的逆向攻坚可能被限流阻塞而非被技术阻塞。

**TA-07【可实现性】MQ Mock 的复杂度未界定**
F-EXEC-06 "Mock 服务管理"对 MQ 协议意味着消息收发 + 异步断言（发送后轮询消费结果），与同步 HTTP Mock 的实现成本不在一个量级，规格未区分。建议 MQ 直接采用 X-EXEC-03 降级路径为主方案。

**TA-08【过度设计】Schema 版本管理（X-ORCH-02）为一周项目引入不必要的复杂度**
断点续跑的 Schema 版本比对机制在 PoC 生命周期内几乎不会触发，建议简化为固定 Schema + 不匹配即整体重跑。

## 三、测试工程师评审意见

**评审维度**：每条 AC 是否可测、口径是否明确

### 问题清单

**TE-01【AC 不可测】E-REQ-01 AC1 的"功能点数"无基准口径**
"条目数与文档中功能点数一致（人工核对）"——什么算一个功能点无预定义，人工核对无判定标准。建议：样例文档预先标注 golden 期望条目数，比对对象从"人的理解"改为"预置基准"。

**TE-02【AC 口径冲突】E-METRIC-02 AC1（固定 /9）与 X-MTR-01（降级缩减分母）矛盾**
AC1 写死"自动化率 = 无人工节点数 / 9"，X-MTR-01 允许降级节点剔除出分母。两处口径冲突将导致演示当天数值无法解释。必须二选一并同步修改另一处。

**TE-03【AC 口径冲突】E-CODE-02 AC1 与 F-REV-02 的非 REST 覆盖要求不一致**
AC1 仅要求"至少 1 种非 REST 协议"，F-REV-02 写"gRPC（proto/service）、SOAP（WSDL/实现类）、MQ（Listener/Producer）至少各识别 1 种"（且该句本身有歧义：是三者各至少一种，还是三者中至少一种？）。AC 是验收依据，规格严于 AC 时按哪个验收？需统一。

**TE-04【AC 判定过弱】E-CODE-02 AC1 的"人工抽查比对"无抽样规则**
未规定抽查样本量与抽样方式（建议：5 个接口全量比对——基数本就只有 5，全比对的成本低于定义抽样规则）。同理适用于 E-REVIEW-01 AC2 的"抽查 3 条定位正确"——样本量 3 过小且无抽样规则，建议提高并固定抽样式。

**TE-05【AC 判定过弱】E-TEST-03 AC1"返回结果"不是有效通过标准**
"执行并返回结果"未区分返回 200 还是 500——任何 HTTP 交互都"返回结果"。应改为"返回结果且完成断言判定（通过/失败二态明确）"。

**TE-06【AC 口径不明】E-REPORT-03 AC2"结果一致"未定义一致口径**
含时间戳/随机字段的服务，响应原文天然不一致。应明确"一致 = 断言结论一致（通过保持通过）"，而非响应体一致。

**TE-07【AC 场景未定义】E-REPORT-02 AC3"人工埋入缺陷"的埋入方式未定义**
埋在业务逻辑层（返回错误数据）还是接口层（返回错误码）会直接影响复测演示的可信度与 Code Review 环节能否同时发现该缺陷（若埋入缺陷可被 E-REVIEW 发现，演示叙事更强）。建议明确定义埋入位置并写入演示脚本。

**TE-08【AC 口径不一致】"缺陷提交"节点语义在度量口径与实现之间不一致**
9 节点口径中的"缺陷提交"在外部语境下指提交至缺陷系统，实现上仅为生成本地缺陷文件（见 PM-03）。E-METRIC-02 实测时该节点会被记为"无人工介入"，但在真实环境中该节点必然人工。口径需在度量方案（F-MTR-01）中显式声明"PoC 口径 ≠ 生产口径"。

**TE-09【AC 验证悬空】G6"里程碑检查"无里程碑可查**
验证方式引用了不存在的排期计划（见 PM-08）。AC 验证手段引用不存在的工件，属于不可测。

**TE-10【AC 可测性弱】E-REQ-01 AC4"明确错误提示"未定义错误提示的可判定形式**
"给出明确错误提示而非静默失败"——建议补最低判定标准：退出码非 0 且 stderr/stdout 含错误类别关键字，使其可自动化验证。
