## 一、版本基线与仓库结构

### 1.1 语言与运行时版本（钉死，禁止漂移）

| 栈 | 版本 | 包管理 |
|----|------|--------|
| Python | 3.11+ | uv（锁定 `uv.lock`） |
| Java | 21（LTS） | Maven（锁定 `pom.xml`） |
| Node | 20 LTS | pnpm（锁定 `pnpm-lock.yaml`） |

### 1.2 Monorepo 结构

```
LLM-AutoTest/
├── docs/                      # 需求与规范文档（现有 01–09）
├── services/
│   ├── orchestrator/          # Python：9 节点编排、断点续跑、REST API
│   ├── java-parser/           # Java：多仓库扫描与接口逆向还原
│   ├── test-executor/         # Python：测试脚本加载与无人值守执行
│   └── frontend/              # Vue 3：任务配置、监控、三视图、报告
├── prompts/                   # 全部 LLM Prompt（版本化，见「五」）
├── schemas/                   # 产物 JSON Schema（见「六」）
├── deploy/                    # docker-compose、Dockerfile、环境配置
└── .github/ 或 .gitlab-ci/    # CI 流水线（见「十」）
```

### 1.3 分工落位

## 二、Python 规范（orchestrator / test-executor）

1. **风格与静态检查**：ruff（lint + format，`line-length = 100`）+ mypy（`strict` 模式起步可放宽至公共 API 强制类型注解，收尾前升 strict）；
2. **命名**：模块 `snake_case`、类 `PascalCase`、常量 `UPPER_SNAKE`；节点实现类统一后缀 `Node`（如 `ReqParseNode`）；
3. **类型注解**：所有对外函数 / 类方法 / 数据模型（pydantic）**强制**类型注解；
4. **数据模型**：跨节点传递的数据结构一律 pydantic BaseModel 定义于 `models/`，与 `schemas/` 中 JSON Schema 一一对应（单一事实来源为 Schema）；
5. **异步**：orchestrator 节点调度用 asyncio；禁止混用线程池与 asyncio 无封装裸调；
6. **注释与 docstring**：中文；模块头部注明对应规格编号（如 `# 对应 F-ORCH-01`），便于验收追溯；
7. **测试**：流水线逻辑（解析、汇总、断点续跑、度量计算）单测覆盖，pytest 组织，测试文件 `test_*.py` 与被测模块同构放置。

## 三、Java 规范（java-parser）

1. **构建**：Maven 标准目录布局；依赖锁定于 `pom.xml`，禁止 SNAPSHOT 依赖进入主干；
2. **静态检查**：checkstyle（Google style 基础上放宽 line-length 至 120）；
3. **解析器**：基于 JavaParser；对 Dubbo / gRPC / 自定义注解的解析策略按可插拔 `ProtocolResolver` 接口实现，新增协议不改主流程；
4. **对外暴露**：REST 接口返回结构与 `schemas/` 中接口还原产物 Schema 对齐（契约见「七」）；
5. **注释**：中文 Javadoc，类头注明对应规格编号（模块 2 / 3，G3、R2）。

## 四、Vue 规范（frontend）

1. **框架**：Vue 3 组合式 API + `<script setup>` + TypeScript；
2. **风格**：ESLint（`eslint-plugin-vue` recommended）+ Prettier；
3. **组件命名**：`PascalCase`，页面组件按 07 六页命名对齐（如 `TaskConfig.vue`、`PipelineDashboard.vue`）；
4. **API 层**：所有后端调用收敛于 `src/api/` 统一层，禁止组件内散落 fetch；
5. **状态**：Pinia；按页面域拆 store，禁止全局单一巨型 store；
6. **展示口径**：界面呈现的度量数值一律来自后端 API 返回的程序化汇总结果，**前端不做任何数值计算或估算**（对应「六」红线 #1）。

## 五、LLM 调用硬约束（红线，AI rule 文件必收）

1. **Prompt 版本化**：所有 Prompt 一律存放于 `prompts/` 目录独立文件（含版本号与变更记录），**禁止在代码中内联 Prompt 字符串**；
2. **参数显式**：temperature / top_p / seed 等采样参数显式配置于配置文件，禁止散落硬编码；
3. **输出校验前置**：LLM 输出必须通过 `schemas/` 对应 JSON Schema 校验成功后才能进入下游产物；校验失败按节点失败处理（走断点续跑口径），禁止降级为「截取可用部分」；
4. **调用留痕**：每次 LLM 调用记录输入摘要、输出、耗时、token 数于节点执行日志，支撑 D6 半自动采集口径；
5. **模型口径**：历史冻结基线记录 GLM-5.3；当前实现按 C-17/C-18 使用 MiniMax-M3/M2.7/M2.5，统一走 OpenAI 兼容接口。除这三个已批准候选外，不得在代码中隐式引入其它模型；模型必须通过环境变量或任务配置显式选择。

## 六、诚实性与产物规范（红线，AI rule 文件必收）

1. **数字不经 LLM**：测试报告、度量报告中的一切数值（通过率、自动化率、接口数、缺陷数）**只能由 execution.json 等结构化产物程序化汇总产生**，禁止由 LLM 生成、改写或「补全」任何数字（F-RPT-02）；
2. **降级必标注**：降级节点按「人工介入」计入并在产物中显式记录降级清单，禁止静默跳过（D1 / D4）；
3. **兜底分列**：兜底仓库的结果单独标注，不与真实仓库产物混算（D5）；
4. **产物 Schema 版本化**：`schemas/` 下每个产物定义含 `schema_version` 字段，结构变更必须升版本，禁止原地改语义；
5. **产物持久化**：所有结构化产物按任务 ID 分目录写入挂载卷，路径约定统一由 orchestrator 的 `artifacts` 模块管理，禁止各节点自行拼路径。

## 七、服务间契约

1. **契约先行**：orchestrator ↔ java-parser、frontend ↔ orchestrator 的 REST 接口，先在 `schemas/contracts/` 定义（OpenAPI 或 JSON Schema），评审通过后双方按契约实现；
2. **向后兼容**：契约变更只允许加字段（可选），删改字段须全服务同步升级并在 deploy 编排中声明启动顺序依赖；
3. **错误结构统一**：三栈错误响应统一 `{code, message, node_id?, details}` 结构；
4. **输入结构**：代码仓库输入采用「路径 + 分支」结构（落实 07 遗留事项 #1 的补全）。

## 八、异常处理与日志

1. 节点失败必须显式落盘（状态 + 原因 + 时间戳），作为 F-ORCH-02 断点续跑的依据；
2. Python 禁止裸 `except:` / `except Exception: pass`；捕获后必须记日志并重新抛出或转为节点失败状态；
3. 日志：Python 用 `logging` 统一配置（JSON 行格式），Java 用 SLF4J；节点日志按任务 ID 归档，支撑 R-MTR-01 九节点口径与 D6 半自动采集；
4. 禁止 `print` 调试代码合入主干。

## 九、Git 工作流

1. **主干开发 + 短分支**：`main` 受保护，特性分支 `feat/`、修复分支 `fix/` 存活不超过 1 天（一周周期内不引入长期并行分支）；
2. **提交信息**：`[服务名] 类型: 摘要`，如 `[orchestrator] feat: 需求解析节点 Schema 校验`；类型限定 `feat/fix/refactor/test/docs/chore`；
3. **合入门禁**：CI 绿灯（见「十」）+ 至少 1 人 review 通过；
4. **禁止** force push 到 main、跳过钩子合入。

## 十、CI 与质量门禁（完整档）

| 环节 | 工具 | 门禁标准 |
|------|------|----------|
| 提交前（本地） | pre-commit（ruff / mypy / checkstyle / eslint） | 本地拦截 |
| Python 单测 | pytest | 覆盖率 ≥70%（流水线核心逻辑） |
| Java 单测 | Maven Surefire | 解析器核心逻辑 ≥70% |
| 前端 | eslint + prettier + vitest 冒烟 | 0 error |
| 构建 | 各服务 Docker 镜像构建成功 | 镜像可启动并通过健康检查 |
| 契约 | 契约测试（schemathesis 或自研校验脚本） | 双方实现符合 `schemas/contracts/` |

排期提示：完整工具链搭建预估 0.5–1 天（M0 内消化，A 牵头 CI 骨架）；若与 G6 冲突，优先砍覆盖率线（≥70% → ≥50%）而非砍门禁本身。

## 十一、容器与部署规范

1. 镜像命名 `llm-autotest/<service>:<版本>`，版本与 git tag 对齐；禁止 `latest` 进入 compose 生产配置；
2. `deploy/docker-compose.yml` 为唯一编排事实来源；环境差异用 `.env` + override 文件表达；
3. 各服务容器必须定义健康检查；启动顺序：持久卷 → java-parser → mock-services → orchestrator → frontend；
4. 产物卷挂载路径统一前缀 `/data/llm-autotest/`，按任务 ID 分目录（承接 08 待定项 #3）。
