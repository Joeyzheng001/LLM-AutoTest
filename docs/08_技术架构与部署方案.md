## 一、技术栈总览（已定稿）

| # | 层次 | 技术 | 选型理由 | 对应规格模块 |
|---|------|------|----------|--------------|
| 1 | 流水线主体 / 后端服务 | **Python** | 全链路生态最全：三格式文档解析（python-docx / openpyxl / markdown）、OpenAI 兼容 LLM 客户端、测试执行引擎、报告与度量汇总均为 Python 强项；团队上手快 | 模块 0（ORCH）、1（REQ）、3（REV 汇总）、4（REVIEW）、5（GEN）、6（EXEC）、7（RPT）、8（DEF）、9（REG）、10（MTR） |
| 2 | Java 接口逆向解析 | **Java（独立服务）** | 被测系统为 Java 多仓库（G3），Java 生态的源码解析工具（JavaParser 等）最成熟，与被测代码同栈可最大限度还原 Dubbo / 自定义注解等复杂框架语义（R2 风险应对） | 模块 2（CODE：多仓库扫描）+ 模块 3（REV：接口还原的 Java 侧解析） |
| 3 | 前端 | **Vue** | 系统部署在 Linux 服务器上供团队使用，需要操作与查看界面；页面方向沿用 [07_UI演示设计.md](07_UI演示设计.md) 的 6 页概念图 | 07 定义的全部页面方向（任务配置 / 流水线总览 / 三视图 / 报告 / 缺陷闭环 / 度量） |
| 4 | LLM | **MiniMax-M3 / M2.7 / M2.5** | 当前生产模型候选；通过 OpenAI 兼容 `/chat/completions` 调用，服务级缺省为 M3，任务级可覆盖 | 所有 LLM 调用环节 |
| 5 | 测试框架 | **待定**（见「五、待定项」#1） | 生成脚本的语法目标与执行引擎载体（F-GEN-03 / F-EXEC-01） | 模块 5（GEN）、6（EXEC） |

**混合架构原则**：Python 为流水线主体，Java 解析以独立服务形式嵌入（Python ↔ Java 通过服务接口交互，而非进程内混合），边界即模块 2/3 与其余模块的规格边界。

## 二、总体架构（多容器）

系统整体容器化，按职责拆分为多个 Docker 容器（容器清单为建议划分，见「五、待定项」#2）：

```
┌─────────────┐   ┌──────────────────┐   ┌──────────────┐
│  frontend   │──▶│  orchestrator    │──▶│ java-parser  │
│ Vue + Nginx │   │ (Python 流水线)   │   │ (Java 解析)   │
└─────────────┘   └───────┬──────────┘   └──────────────┘
                          │ ▼
              ┌───────────┴───────────┐
              │  test-executor (Python) │──▶ mock-services (多协议)
              └───────────┬───────────┘
                          │
                     MiniMax API（外部）
```

| 容器 | 技术栈 | 职责 | 对应规格 |
|------|--------|------|----------|
| frontend | Vue + Nginx | 任务配置、流水线监控、三视图展示、报告/缺陷/度量查看 | 07 全部 6 页方向 |
| orchestrator | Python | 9 节点编排、断点续跑、产物管理（统一入口命令在此容器内保留） | 模块 0（F-ORCH-01/02） |
| java-parser | Java | Java 多仓库扫描与接口逆向还原 | 模块 2 / 3（G3、R2） |
| test-executor | Python | 测试脚本加载与无人值守执行、断言二态判定 | 模块 6（E-TEST-02） |
| mock-services | 按协议 | gRPC / GraphQL / SOAP / MQ 的 Mock 执行环境 | F-EXEC-06、R3 降级策略 |

## 三、部署方案（已定稿）

- **目标环境**：Linux 服务器，供团队多人使用
- **部署形态**：**多 Docker 容器化部署**——从维护角度出发，各组件独立容器、独立升级、独立扩缩，故障隔离，避免单一大镜像的维护泥潭
- **交互入口**：
  1. 团队日常使用：Vue 前端界面（Web）
  2. 基线口径兼容：orchestrator 容器内保留「一条命令 + 配置文件」的统一入口（F-ORCH-01 口径不因部署形态改变）
- **产物与状态**：结构化产物（execution.json、缺陷记录、回归资产树等按 R-RPT-02 / R-REG-02 口径为文件形态）通过挂载卷持久化；卷规划见「五、待定项」#3
