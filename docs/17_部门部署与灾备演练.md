# 部门部署与灾备演练

配套验收记录请使用 [内部部署验收记录模板](18_内部部署验收记录模板.md)；每项必须附真实环境证据，
不能用本地单测替代。

## 适用范围

本方案面向部门内部服务器或部门内网可达的部署环境。公网地址、开发机端口映射和从外网发起的
探测均不作为上线验收依据；被测服务、内部 LLM 中转站、数据库和对象存储的访问路径以内部网络策略为准。

## 内部服务器验收输入

开始部署前只需确认以下信息，不把密码、Token 或私钥写入本仓库：

| 信息 | 用途 |
|---|---|
| 部署机系统、Docker/Compose 版本、CPU/内存/磁盘 | 判断容器与并发上限，规划持久卷 |
| 部门 DNS 或内网访问地址、入口端口、TLS/反向代理方式 | 验证前端入口和健康检查，不依赖公网 IP |
| PostgreSQL 地址、数据库名、备份落点 | 注入完整 `DATABASE_URL`，执行迁移和恢复演练 |
| 对象存储方案（MinIO/部门 S3/OSS）及 bucket | 保存大产物并验证 `/ready` 探活 |
| SecretStore 主密钥、访问令牌映射的注入方式 | 保证跨实例重跑和项目权限，不进入日志或 Git |
| 内部 LLM 中转站地址、协议、可用模型别名和限流策略 | 验证真实网关调用、超时、并发和断点重跑；不要求部署机直连模型厂商 |
| 被测服务/E2E 前端的内网地址、证书策略 | 验证接口与浏览器能从部署机访问目标系统 |

## 启动顺序

如需按固定顺序启动，可直接执行仓库内的一键编排脚本（默认启动 2 个 orchestrator 实例）：

```sh
COMPOSE_ENV_FILE=deploy/.env APP_URL=http://部门入口 \
  sh deploy/department_bootstrap.sh
```

脚本不会删除数据库、卷或历史产物；`DRY_RUN=1` 可在部署窗口前只打印执行顺序，且不读取或输出
环境文件内容。需要单实例时显式设置 `ORCHESTRATOR_REPLICAS=1`。若部门入口仅在测试环境使用
自签名 HTTPS，必须显式设置 `ACCEPTANCE_INSECURE_TLS=1`；生产证书应保持默认严格校验。

1. 配置 `deploy/.env`：PostgreSQL 用户/密码和完整 `DATABASE_URL`（密码先 URL 编码）、
   `SECRETS_ENCRYPTION_KEY`、访问令牌映射、LLM 中转站和 `JOB_MAX_CONCURRENCY`；如使用本地源码目录，
   设置 `REPOSITORIES_HOST_ROOT` 为部署机实际路径（Windows Docker 主机填写已共享的 `C:/...` 目录，
   容器内统一映射到 `/opt/repos`；容器内 `REPOSITORIES_ROOT` 保持 `/opt/repos`）。
   启用对象存储时保留已验证的 `MINIO_IMAGE` 固定版本；升级镜像时显式改版本，不使用 `latest`。
2. 在启动容器前执行
   `docker compose -f deploy/docker-compose.department.yml --env-file deploy/.env run --rm --no-deps orchestrator .venv/bin/python -m orchestrator validate-deployment`；该命令只校验 PostgreSQL URL、SecretStore、访问令牌、模型和对象存储配置，不连接外部服务，也不会输出密钥。
3. 启动 PostgreSQL 和 Java Parser，执行一次 `.venv/bin/python -m orchestrator migrate-db`；
   `init-db` 仍可作为兼容别名，但生产升级统一使用带版本记录的迁移入口。
4. 启动编排服务、前端和 Prometheus。多实例使用 `docker compose ... up -d --scale orchestrator=2`；编排服务不绑定宿主机端口，由前端 Nginx 通过 Docker DNS 动态解析服务名；Prometheus 同样使用 DNS 服务发现抓取全部实例；前端和 Prometheus 等待 orchestrator `/ready` 健康后再启动（若使用普通 Compose，先确认共享卷行为，再考虑 Swarm/Kubernetes）。代理层不自动重试 POST，避免重复提交/重跑。
5. 需要 MinIO 时追加 `--profile object-store`，并配置 `ARTIFACT_STORAGE_BACKEND=s3`、bucket 和访问凭据；内部生产可替换为部门统一 S3/OSS。
6. 验证 `/health`、`/ready`、`/metrics`；启用 MinIO/S3 时确认 `/ready` 返回
   `object_storage=ok`，再运行 `python deploy/acceptance_smoke.py --url <部门入口>` 完成统一入口验收。
   探针会校验 `health.status=ok`、`ready.status=ready` 以及 Prometheus 指标正文，避免前端 SPA 的
   200 HTML 被误判为后端已就绪；
   并运行 `deploy/load_smoke.py` 采集只读端点基线。共享部署若需验证鉴权 API，使用环境变量
   `AUTOTEST_ACCEPTANCE_TOKEN` 和 `AUTOTEST_ACCEPTANCE_PROJECT_ID`，不要把令牌写进命令行或日志。

## 备份与恢复演练

- 定期执行 `deploy/backup_postgres.sh`，脚本会先写入权限为 0600 的临时文件，成功后原子移动为最终 dump，并生成 `.sha256` 校验文件；备份文件纳入部门备份系统并记录保留期。
- 在隔离恢复库执行 `deploy/restore_rehearsal.sh <dump-file>`，脚本会先检查文件非空、校验和及 `pg_restore --list` 可读，再执行隔离库重建，验证 `jobs/job_nodes/job_events/artifacts` 可查询。两个脚本均应保留可执行权限；受限执行环境可等价使用 `bash deploy/<script>.sh`。
- 恢复任务目录或对象存储证据后，使用 `migrate-artifacts` 幂等补登记；不直接覆盖现有任务目录。
- 记录 RPO（可接受的数据丢失窗口）、RTO（恢复到可接任务的时间）和最后一次演练时间，纳入发布验收。

## 运行边界

- PostgreSQL 保存任务状态、租约、归属、审计和产物索引；大文件不写入数据库。
- PostgreSQL `job_configs` 保存脱敏任务配置版本；`job_input.json` 或本地卷不可见时，服务可从快照恢复非敏感参数，需求文档再按对象存储索引尝试还原。
- 同一 job 的实际执行仍由数据库租约串行化；多实例共享数据库后不会重复跑同一 job。
- 本地文件卷是兼容回退；部门部署应启用对象存储镜像并为 `artifacts` 卷配置持久化/备份。
- 内部服务器验收还需验证：双实例能访问同一 PostgreSQL/对象存储、能访问内网被测服务和 LLM 网关，
  前端入口可由部门 DNS/反向代理访问，且不依赖开发机本地路径。
