# 用户故事卡片：LLM-AutoTest

- **拆分依据**：[02_立项提案.md](02_立项提案.md)
- **拆分日期**：2026-09-14
- **优先级定义**：
  - **P0**：不完成则验收演示无法进行（对应风险 R1/R2 的关键路径）
  - **P1**：不完成则 G1–G5 验收目标部分落空
  - **P2**：体验加分项，缺失不影响闭环成立
- **实现深度约定（对应评审 TA-01）**：P0 卡片按完整实现；P1 卡片统一按最小可用实现（每卡片 1 个最小场景），以匹配一周容量与 4 人人力假设（见立项提案「六、一周排期计划」）

## Epic 1：需求输入通道（E-REQ）

对应目标 G2。

### E-REQ-01 需求文档多格式解析

> **作为** 测试专项小组成员，**我希望** 系统能自动解析 Word / Markdown / Excel 三种格式的需求文档并抽取结构化需求条目，**以便** 后续 Code Review 与用例生成环节可以直接消费标准化输入。

**验收标准（AC）**：
- [ ] AC1：给定 1 份 Word 格式需求样例文档，解析产出结构化需求条目 JSON，条目数与预置的 golden 期望条目数一致（样例文档预先人工标注功能点基准，比对对象为预置基准而非现场人工判断，对应评审 TE-01）
- [ ] AC2：给定 1 份 Markdown 格式需求样例文档，解析产出同构 JSON，通过同一 Schema 校验
- [ ] AC3：给定 1 份 Excel 格式需求样例文档，解析产出同构 JSON，通过同一 Schema 校验
- [ ] AC4：对格式不符或空文档输入，给出明确错误提示而非静默失败（可判定形式：进程退出码非 0，且 stderr 输出含错误类别关键字 `[REQ-ERROR]`，可自动化验证，对应评审 TE-10）

**优先级**：P0（Code Review 与用例生成的前置输入）

## Epic 2：代码输入通道（E-CODE）

对应目标 G3，风险 R2 的攻坚对象。

### E-CODE-01 Java 多仓库代码扫描

> **作为** 测试专项小组成员，**我希望** 系统能扫描指定的多个 Java 仓库（≥2 个）并汇总可分析的源码清单，**以便** 后续接口逆向解析有统一的代码输入。

**验收标准（AC）**：
- [ ] AC1：对 2 个指定 Java 仓库执行扫描，输出含仓库、模块、源码文件路径的结构化清单
- [ ] AC2：扫描过程无人工操作（只需启动命令时指定仓库路径）
- [ ] AC3：对不存在的仓库路径给出明确错误提示

**优先级**：P0

### E-CODE-02 LLM 接口逆向还原

> **作为** 测试专项小组成员，**我希望** LLM 能从 Java 源码中逆向还原接口定义（路径、方法、入参、出参、协议类型），**以便** 在无接口文档的前提下获得接口结构化清单作为唯一接口来源。

**验收标准（AC）**：
- [ ] AC1：对演示仓库中至少 5 个接口（含 REST 与至少 1 种非 REST 协议），还原出结构化接口定义，路径/方法/参数名与源码一致（基数仅 5，采用全量逐接口人工比对，不另行定义抽样规则，对应评审 TE-04）
- [ ] AC2：还原产物为结构化 JSON，通过预定义 Schema 校验
- [ ] AC3：对无法解析的文件输出"跳过 + 原因"记录，不中断整体流程

**优先级**：P0（全流水线的最高风险项，对应 R2）

## Epic 3：Code Review 环节（E-REVIEW）

对应目标 G4。

### E-REVIEW-01 需求-代码映射表生成

> **作为** 测试专项小组成员，**我希望** 系统能逐条比对需求条目与还原的接口/代码实现，产出需求-代码映射表，**以便** 它作为上游产物派生风险清单与遗漏功能清单。

**验收标准（AC）**：
- [ ] AC1：映射表覆盖输入需求条目的 100%，每条需求标注"已实现 / 部分实现 / 未实现 / 无法判断"四态之一
- [ ] AC2：每条"已实现"条目附带对应代码位置（仓库 + 文件 + 方法名），按固定抽样规则人工比对定位正确（抽样规则：按条目 ID 升序取前 5 条，不足 5 条全量，对应评审 TE-04）
- [ ] AC3：映射表为结构化产物（JSON/MD），可被下游程序消费

**优先级**：P0（三种产物的上游）

### E-REVIEW-02 风险清单与遗漏功能清单生成

> **作为** 测试专项小组成员，**我希望** 基于映射表自动派生风险清单和遗漏功能清单两种视图，**以便** 测试团队直接获得评审结论性产物。

**验收标准（AC）**：
- [ ] AC1：风险清单中每项风险包含"风险描述 + 对应需求条目 + 代码位置"三要素
- [ ] AC2：遗漏功能清单与映射表中"未实现"条目 100% 一致（可程序校验）
- [ ] AC3：三种产物（映射表/风险清单/遗漏清单）一次生成、三种视图输出，无需三次独立调用

**优先级**：P1

### E-REVIEW-03 LLM 产物人工审核

> **作为** 测试专项小组成员（人工审核角色），**我希望** 对 LLM 关键产物（接口还原清单、需求-代码映射表、生成的用例脚本）进行人工审核并记录结论，**以便** 落实"用例模板维护 / LLM 生成执行 / 人工审核"协作模式，被驳回的产物有明确回流路径（对应澄清记录 #4 与评审 PM-01）。

**验收标准（AC）**：
- [ ] AC1：审核对象至少覆盖接口还原（`interfaces.json`）与映射表（`mapping.json`）两类关键产物，每类给出"通过 / 驳回"结论
- [ ] AC2：驳回结论必须附驳回原因（如参数还原错误、映射定位错误），审核记录以结构化文件（`review_log.json`）落盘
- [ ] AC3：被驳回的产物标记"待修正"，回流至对应生成节点重跑或人工修正后重新提交审核，运行中完成至少 1 次完整"驳回 → 修正 → 复审"闭环

**优先级**：P1（最小可用：以 1 次完整驳回回流闭环为准）

**口径说明**：人工审核不在 9 节点自动化率口径内（审核本身为人工角色，不改变 9 节点清单），审核结论仅作为产物质量记录（见规格 R-MTR-01/R-REVW-05）。

## Epic 4：用例生成与执行（E-TEST）

对应目标 G1 中间环节，风险 R3/R4 的覆盖对象。

### E-TEST-01 LLM 测试用例生成

> **作为** 测试专项小组成员，**我希望** LLM 基于还原的接口定义和需求条目自动生成可执行测试脚本（覆盖正常、边界、异常场景），**以便** 无需人工从零编写接口测试脚本。

**验收标准（AC）**：
- [ ] AC1：对至少 5 个已还原接口，每接口生成 ≥3 条用例（正常/边界/异常各 ≥1）
- [ ] AC2：生成的用例参数结构与接口还原定义一致（无虚构参数名，可程序校验）
- [ ] AC3：生成的脚本在选定的测试框架下语法合法（可被框架加载，不抛解析错误）

**优先级**：P0

### E-TEST-02 测试框架选型与执行引擎

> **作为** 测试专项小组成员，**我希望** 选定一套测试框架并搭建执行引擎，**以便** 生成的测试脚本可以无人值守自动执行。

**验收标准（AC）**：
- [ ] AC1：产出选型说明文档，含 ≥2 个候选框架的对比和选定理由
- [ ] AC2：一条命令触发全量用例执行，执行过程无人工操作
- [ ] AC3：需鉴权/前置数据（登录态、token、上游造数）的被测接口，前置数据在流程启动前预置于执行配置（fixtures），执行引擎自动加载，节点内无人工介入（对应评审 PM-02）
- [ ] AC4：执行结果以结构化形式输出（每用例：通过/失败 + 失败原因）

**优先级**：P0

### E-TEST-03 多协议执行覆盖

> **作为** 测试专项小组成员，**我希望** 执行引擎支持 REST、gRPC、GraphQL、SOAP、MQ 五种协议的用例执行，**以便** 验证路径对全协议范围的适用性。

**验收标准（AC）**：
- [ ] AC1：REST 协议：≥5 条用例对真实（或 Mock）服务执行并完成断言判定（通过/失败二态明确；仅"返回结果"不构成通过，对应评审 TE-05）—— **P0 部分**
- [ ] AC2：gRPC、GraphQL 协议：各 ≥1 条用例执行并完成断言判定（可用 Mock 服务）
- [ ] AC3：SOAP、MQ 协议：各 ≥1 条用例执行并完成断言判定；若环境不可用，降级为"脚本生成成功 + Mock 执行演示"并在报告中注明降级（降级场景不计入 G1"跑通"，见立项提案 G1 判定标准；其中 MQ 以降级路径为主方案，对应评审 TA-07）

**优先级**：P1（其中 REST 部分 P0，其余按 R3 应对策略允许降级）

## Epic 5：报告与缺陷闭环（E-REPORT）

对应目标 G1 后半段，风险 R7 的覆盖对象。

### E-REPORT-01 测试报告自动生成

> **作为** 测试专项小组成员，**我希望** 执行结束后自动生成测试报告（汇总通过率、失败明细），**以便** 无需人工汇总即可向上游呈现执行结论。

**验收标准（AC）**：
- [ ] AC1：报告自动包含：总用例数、通过数、失败数、通过率、失败用例明细（含失败原因）
- [ ] AC2：从执行结束到报告产出无人工操作
- [ ] AC3：报告数值与执行引擎原始输出一致（可程序校验）

**优先级**：P0

### E-REPORT-02 缺陷清单生成与复测

> **作为** 测试专项小组成员，**我希望** 失败用例自动转化为缺陷清单，并在修复后能对缺陷清单发起复测，**以便** 形成"发现 → 提交 → 复测"的缺陷闭环。

**验收标准（AC）**：
- [ ] AC1：每个失败用例转化为一条缺陷记录，含"接口、失败原因、复现步骤（即用例脚本引用）"
- [ ] AC2：对已修复的缺陷，一条命令发起复测，复测结果更新缺陷状态（通过 → 关闭建议，仍失败 → 保留）
- [ ] AC3：验收场景中完成至少 1 次完整"缺陷产生 → 复测通过 → 关闭"闭环（人工埋入缺陷实现；埋入位置固定为业务逻辑层——在演示仓库独立分支上使接口返回错误数据，埋入方式与预期失败用例写入演示脚本，对应评审 TE-07）

**优先级**：P1

### E-REPORT-03 回归脚本沉淀

> **作为** 测试专项小组成员，**我希望** 复测通过的用例自动沉淀为回归自动化脚本资产（纳入固定目录/套件），**以便** 后续回归直接复用，无需重新生成。

**验收标准（AC）**：
- [ ] AC1：复测通过的用例自动进入回归脚本目录，且带有需求/接口溯源信息
- [ ] AC2：沉淀后的脚本可被回归执行命令直接重跑，断言结论一致（"一致"= 断言结论一致即"通过保持通过"，不要求含时间戳/随机字段在内的响应体原文一致，对应评审 TE-06）
- [ ] AC3：回归目录结构化（按协议或需求维度组织），并有资产清单

**优先级**：P1（基于 REST 最小闭环先行实现，对应 R7 应对策略）

## Epic 6：度量与验收（E-METRIC）

对应目标 G5 与整体验收交付。

### E-METRIC-01 自动化率度量方案设计

> **作为** 测试团队负责人，**我希望** 有一份"无人工操作节点数 / 总节点数"的度量方案（9 节点口径定义 + 采集方法），**以便** 自动化率有统一、可复现的度量标准。

**验收标准（AC）**：
- [ ] AC1：方案文档明确定义 9 个流程节点（需求解析、代码扫描、接口还原、用例生成、执行、报告、缺陷提交、复测、回归沉淀）各自的"人工介入判定标准"
- [ ] AC2：给出数据采集方法（何种操作被记录、如何统计），在本项目中可实际执行

**优先级**：P1

### E-METRIC-02 自动化率首次实测

> **作为** 测试团队负责人，**我希望** 在验收演示流程中实测一次自动化率数值，**以便** 获得第一个基线数据支撑项目结论。

**验收标准（AC）**：
- [ ] AC1：验收当天全流程跑一遍，记录各节点是否人工介入，产出自动化率 = 无人工节点数 / 9 的具体数值（分母固定为 9：被降级跳过的节点按"人工介入"计入并在报告注明，口径与规格 X-MTR-01 统一，对应评审 TE-02）
- [ ] AC2：对每个人工介入节点给出瓶颈原因分析（对应 R5 应对策略）

**优先级**：P1

### E-METRIC-03 验收日交付与彩排

> **作为** 测试团队负责人，**我希望** 验收日有完整彩排过的端到端演示（含降级预案），**以便** 项目结论可信呈现。

**验收标准（AC）**：
- [ ] AC1：验收前完成 ≥1 次完整端到端彩排，演示输入锁定（对应 R4 应对策略）
- [ ] AC2：每个 P0/P1 卡片的验收场景在验收脚本中有对应环节
- [ ] AC3：第 2 天末完成范围检查点（对应 R1 应对策略）：未跑通环节标记降级方案（路径演示 + 界面演示）

**优先级**：P0
