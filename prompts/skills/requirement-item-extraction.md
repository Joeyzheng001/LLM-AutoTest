## 适用节点

仅用于 `req_parse` 的需求条目提取。不得把本文用于代码实现判断、测试用例生成或需求质量评分。

## 输入契约

- 输入是一个或多个带 `[SRC-...]` 编号的需求原文片段；批次头给出当前批次编号。
- `source_id`、REQ ID 和 CLM ID 由系统管理。模型只能引用本批实际出现的 `source_id`。
- 已有需求基线时，输入只包含差异分析后仍有效的新增/修改范围；删除项只作为影响核查背景，不恢复为当前需求。差异项附有 `DIF` 范围说明和来自基线/被测文档的原文 `SRC` 片段；claim 必须引用支持当前有效需求的原文片段，不能只引用合成的差异摘要。

## 工作步骤

1. 先辨别需求、背景说明、术语和示例；只将明确的系统行为、约束、质量目标或依赖作为需求。
2. 按“一个可以独立判断是否满足的声明”拆分。把主流程、输入校验、边界、异常、权限、状态变化、数据一致性、非功能目标拆成不同 claim；不得把正常与异常行为塞进同一 claim。
3. 把同一业务主题的 claim 放在一个 item；仅在确属重复时合并，并保留全部相关 source refs。不得跨无关主题合并，也不得为了凑数量拆分同义句。
4. 每个 item 与 claim 分别引用最直接的原文 source refs。一个声明横跨多个片段时可引用多个；引用必须来自当前批次。原文含糊或矛盾时照实保留，不替用户裁决。
5. 只有原文明确给出优先级时填写 `priority`。其他情况下不按业务常识推断 P0/P1/P2。
6. 验收条件只摘录明确、可观察的原文条件。缺少预期、角色、前置状态或阈值时留待需求评审，不自行补齐。

## 输出契约

只返回主 Prompt 定义的 `items` JSON。每项提供简短 `title`、可选且有原文依据的 `priority`、`source_refs` 和非空 `claims`；每个 claim 提供 `kind`、`statement`、可选 `acceptance_criteria`。不得生成程序编号、来源目录字段、评分、总结、风险清单、思维导图或用例。

## 禁止事项

- 不得引用输入中未出现的 source ID；不得伪造行号、章节号或原文。
- 不得把隐含实现方案、行业惯例、测试建议写成需求事实。
- 不得把需求“改写得更完整”来掩盖原文缺口；不确定内容要保持不确定。
- 不得返回空 claim、纯标题型 claim、重复 claim 或嵌套需求树。
- 不得将上批或下批的信息并入本批输出。

## 提交前自检

逐项确认：每个 item 至少有一个 claim；每个 claim 只有一个可验证陈述；引用均属于当前批次；验收条件可在原文定位；正常/边界/异常和权限/状态等差异未被合并；没有新增业务规则。

## 失败策略

当前批没有需求时按主 Prompt 返回空 `items`。如果需求确实无法拆成可验证声明，仍忠实返回最小原子陈述并引用来源；由评审节点标记待澄清，不要编造。无法满足 JSON 契约时只修复结构，不改变业务语义。

## 验收样例

输入原文：“连续输错密码 5 次后锁定账户 15 分钟；成功登录后清零失败次数。”

- 合格拆分：至少两个 claim，分别是“连续 5 次失败触发 15 分钟锁定”和“成功登录后失败次数清零”，各自引用同一原文 source ID。
- 不合格：一个 claim 写成“实现登录、校验密码、锁定账户并记录日志”；加入未说明的解锁方式；自行标 P0；或为 15 分钟补造配置位置。

回归场景必须覆盖：合法 items；别名/包装字段由受控兼容层处理；缺少来源引用；跨批引用；复合行为未拆分；长段落/超长输出按批边界处理。
