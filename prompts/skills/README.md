# LLM 节点 Skill 治理

Skill 是节点调用前受控加载的操作规程，不是可执行指令。约束优先级：系统安全与 Schema > 当前节点 Prompt/输出契约 > Skill > 经审核的长期记忆 > 模型自由发挥。Skill 不放宽 Schema，也不能代替程序门禁或来源证据。

## 配置粒度

按实际 `load_prompt` 的模型任务配置 Skill，不按九个编排节点机械地一对一配置。一个编排节点可调用多个模型任务；每个任务只加载自身所需的任务规则、共用输出规则与审核记忆。纯程序节点不加载 Skill。映射在 `services/common/src/common/prompts_loader.py` 的 `_NODE_KNOWLEDGE`，调用记录的 `knowledge_refs` 保存实际加载版本。

例如 Code Review 的证据筛选、业务评审、测试预期与变更影响分别配置；E2E 的场景规划、页面事实提取、用例生成、用例复核和运行时控件重定位分别配置；单元测试的场景规划和源码生成分别使用独立 Skill。不得因某任务与同一编排节点相邻，就自动继承其 Skill。

## 必需章节

每份节点 Skill 必须说明：适用节点、输入契约、可复现工作步骤、输出契约、禁止事项、自检、失败策略和至少一个验收样例。涉及多个 artifact 的节点必须说明父子关系与程序生成字段；证据类 Skill 必须定义什么能证明/不能证明结论。

## 需求解析与评审边界

- 条目抽取先拆单一可验证 claim，再保留来源；REQ/CLM/SRC 编号、评分、等级、摘要与页面树由程序生成。
- 需求质量评审只生成带 claim/source 引用的问题发现。不得在模型端重复生成分数和 UI 派生结构，减少无关自由度与字段漂移。
- 需求变更模式只能针对差异输入；删除项不转换成当前有效功能或正向用例。

## Code Review 边界

- 以 claim 而非整条 REQ 为审查单位；一条 REQ 可有多个声明、接口和证据。
- 结论逐条引用系统分配的 EVD ID；原文、接口目录、文件名、路径和搜索词命中不单独构成行为证据。
- 证据目录中的源码片段必须先限定范围和脱敏；页面将结论、位置、脱敏片段关联展示。
- 无证据或扫描覆盖不足时 `undetermined`；“没搜到”不等于 `missing`。程序门禁必须检查本声明引用的相关证据，不能只检查全仓是否出现某类别。

## 稳定性与分批

1. 长输入按 source/claim/interface 等实体分批，并显式给出 batch index/total；仅基于当前批输出。
2. 输出 Schema 尽可能小；模型只返回语义结果，稳定 ID、引用目录、评分和聚合字段由程序生成。
3. 兼容层只处理可证明等价的包装、命名别名或单对象容器；不能通过删除未知业务字段、补默认规则、搜索任意嵌套字段或跨节点串产物“修好”输出。
4. 失败最多执行一次定向 JSON 修复；修复后重新经过业务校验、ID 覆盖、证据引用和 Schema。仍失败就保存错误上下文并人工介入。

## 变更与验收

改动 Prompt、Skill、Schema、归一化代码时需同步更新版本与 changelog，并核对受影响下游消费者。验收案例至少覆盖：合法 JSON、字段漂移、缺字段/非法 ID、超长分批、无证据/低扫描覆盖、拒绝臆造；Code Review 另覆盖同类但不相关证据、单需求多接口，需求侧另覆盖多来源和复合句拆分。

真实模型的质量验收与结构验收分开：Schema 通过只表示结构合规，不代表语义质量；通过固定 golden 文档/仓库记录 claim 覆盖、来源可追溯率、无证据误判率、重复率和人工采纳率。没有基线数据时不宣称质量提升。
